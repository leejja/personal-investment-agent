실제 호출 결과: `ka10099`(mrkt_tp=0, KOSPI)가 **2,481종목을 단일 호출로 반환**(페이지네이션 없음, `cont_yn=N`). `mrkt_tp` 값(0=코스피, 10=코스닥, 8=ETF, 60=ETN 등)은 원본 코드 주석에서 그대로 확인했다 — ETF/ETN이 일반 주식과 다른 `mrkt_tp`로 완전히 분리되어 있어, KOSPI/KOSDAQ만 조회하면 구조적으로 ETF가 섞이지 않는다.

## 4. Candidate Discovery 설계 검토 2차 — 데이터 확인 후

실측 데이터를 근거로 재설계했다. 1차 검토와 달라진 결론은 없다 — **여전히 별도 Agent가 아니다.** deterministic 필터링에 쓸 실제 데이터가 생겼어도, "투자 판단을 내리는 reasoning" 단계는 여전히 없기 때문이다. LLM이 필요한 지점은 자유 텍스트 → 구조화(Supervisor의 routing과 동일 성격)뿐이다.

핵심 설계 결정:

- **Candidate Discovery는 Supervisor와 같은 2단 구조**(`filter_intent.py` + `orchestrator.py`)로, Agent의 3단 패턴(analysis/reasoning/orchestrator)을 따르지 않는다.
- **sector_terms/size_terms는 매 요청마다 실측된 값에 대해서만 grounding**한다 — LLM에게 실제 관측된 업종/규모 목록을 프롬프트에 제공하고 그 안에서만 고르게 한 뒤, Python이 다시 검증한다(Portfolio Agent의 symbol grounding과 동일 원리).
- **후보 과다 시 momentum ranking(`ka10019`)을 기본값으로 쓰지 않는다** — 정렬 기준 선택 자체가 암묵적 투자 전략(모멘텀 선호)을 시스템이 강제하는 것이라고 판단했다. 대신 한도 초과 시 subset을 고르지 않고 Stock Research를 아예 실행하지 않는다.
- **Stock Research Agent가 담당하는 매력도 평가, Portfolio Strategy Agent가 담당하는 BUY/AVOID 판단을 중복하지 않는다** — Candidate의 `matched_filters`에는 점수/매력도를 절대 담지 않는다.

## 5. 구현 전 미세조정 3가지 (사용자 지시)

1. **`MAX_STOCK_RESEARCH_FANOUT`**: 이름 자체에서 "투자 threshold나 top-N 선택값이 아니라 Stock Research fan-out의 실행/비용 안전 한도"라는 의미가 드러나도록 명명했다(`MAX_CANDIDATES` 같은 모호한 이름 대신). 후보가 한도를 초과하면 일부를 선택하지 않고 Stock Research를 0건 실행한 뒤 조건을 더 좁혀달라고 요청하는 정책은 그대로 유지.
2. **`exclude_owned`**: `portfolio_strategy` intent를 탄다는 사실만으로 강제하지 않는다. `DiscoveryFilter` grounding이 사용자 문장("내 포트폴리오에 없는", "미보유" 등)만 보고 독립적으로 판단하도록 프롬프트를 설계했다 — Portfolio Strategy를 쓴다는 사실과 보유종목 제외 여부를 별개 개념으로 유지.
3. **`Candidate.matched_filters`**: `list[str]`(예: `["market:kospi"]`) 대신 `dict[str, str]`(예: `{"market": "kospi"}`)로 설계했다 — 새 Pydantic 모델을 추가하지 않으면서도(과설계 회피) REST API/모바일 UI에서 문자열 파싱 없이 바로 쓸 수 있는 최소 구조.

설계 원칙 그대로 구현에 반영한 것들:

- `DiscoveryOrchestrator.run()`은 조건이 없으면 `None`을, 조건은 있으나 실행 불가(과다 등)면 `DiscoveryError`를 raise한다. 두 경우를 구분해야 `candidate_discovery`(조건 없음=실패)와 `portfolio_strategy`(조건 없음=보유종목 폴백, 조건 있으나 실패=전체 요청 실패)가 서로 다른 정책을 적용할 수 있다.
- discovery로 찾은 종목 집합은 사용자가 이름을 부른 특정 종목이 아니라 시스템이 찾아낸 후보이므로, `portfolio_strategy`의 explicit-symbol 경로(필수 dependency, 실패 시 전체 실패)가 아니라 기존 보유종목 fan-out과 동일한 skip-허용 경로(`_run_stock_research_fanout`)를 그대로 재사용한다.
- `PortfolioContext` 조회는 `candidate_discovery`/`portfolio_strategy` 양쪽에서 필요해질 수 있어(`exclude_owned`가 어느 쪽에서도 나올 수 있음) `_fetch_portfolio_context()` 공통 helper로 추출했다.

## 11. REST API v1 (세션 2)

Market/Stock Research/Portfolio Strategy Agent, Supervisor/Router, Candidate Discovery까지 완성된 뒤, 현재 Core를 실제 서비스처럼 써보기 위해 FastAPI 기반의 얇은 REST API v1을 설계·구현했다. 목표는 새로운 투자 로직을 만드는 게 아니라 기존 `SupervisorOrchestrator`를 외부 client에서 호출할 수 있는 최소 API boundary를 만드는 것이었다.

### 11.1 설계 검토 먼저 진행

구현 전에 `app/main.py`(빈 stub 확인), `SupervisorOrchestrator`의 실제 생성자/`run()` 시그니처, 전체 커스텀 예외 7종(`RoutingError`/`SupervisorError`/`DiscoveryError`/`FilterIntentError`/`ReasoningError`×3), 그리고 **각 Service의 API key 전달 방식**을 코드로 직접 확인했다.

가장 중요한 발견: `app/services/ecos.py`는 API key를 URL 경로 세그먼트에 그대로 넣고(`.../StatisticSearch/{api_key}/json/...`), `app/services/opendart.py`는 쿼리 파라미터(`crtfc_key`)로 그대로 넣는다. `httpx.HTTPStatusError` 등 예외의 기본 `str()`에는 request URL이 포함되므로, 이 두 Service에서 올라온 미분류 예외를 그대로 client에 전달하면 API key가 그대로 유출된다는 걸 실제 코드로 확인했다 — 이게 error mapping 설계의 핵심 근거가 됐다.

### 11.2 구현 전 3가지 명확화 (사용자 지시)

1. **`UserRequest`에 `investor_profile`을 추가하지 않는다.** `SupervisorOrchestrator.run(request, investor_profile=...)`이 이미 이 둘을 의도적으로 분리하고 있으므로, HTTP transport 편의를 위해 Core domain model을 바꾸지 않는다. 대신 API 레이어 전용 `AnalysisRequest` DTO(`app/api/routes.py`)에서만 받아 endpoint가 둘로 나눠 넘긴다.
2. **`get_supervisor(request: Request)` dependency**를 `routes.py` 안에 최소로 두어 `app.dependency_overrides`로 테스트에서 실제 fake Supervisor를 주입할 수 있게 한다. 별도 `dependencies.py`나 DI 프레임워크는 만들지 않는다.
3. **502의 의미를 API 정책으로 명시적으로 문서화한다** — 단순 네트워크 게이트웨이 오류가 아니라 routing/filter-intent/reasoning 같은 이 프로젝트의 LLM 기반 dependency를 통해 요청을 정상 완료하지 못한 경우를 가리킨다(README/dev-log 양쪽에 기록).

### 11.3 구현

```text

app/api/
├── main.py           # FastAPI 앱, lifespan(의존성 그래프 1회 생성), 예외 핸들러 8개 등록
└── routes.py         # AnalysisRequest DTO, get_supervisor, GET /health, POST /analysis
```

- `lifespan`에서 `KiwoomService`/`EcosService`/`OpenDartService`/`LLMService`와 그 위의 Orchestrator 전체를 `scripts/supervisor_demo.py`와 동일하게 구성해 **프로세스 생애주기 동안 1회만** 생성한다. `KiwoomService.get_access_token()`의 instance-level 캐싱이 여기서도 그대로 유효하다.
- `asyncio.Lock`(KiwoomService의 token lock)은 Python 3.12+에서 첫 `acquire()` 시점에 실행 중인 loop에 lazy 바인딩되고, `lifespan`의 startup 코드 자체가 이미 실행 중인 event loop 안에서 돌기 때문에 안전함을 확인했다(기존 스크립트들과 동일한 안전성).
- Service 레이어의 httpx client가 매 호출마다 새로 열리는 기존 패턴(`async with httpx.AsyncClient(...)`)은 FastAPI가 만드는 문제가 아니라 이미 있던 특성이라 이번 범위에서 리팩터링하지 않았다.
- 예외 핸들러 3종(`_external_dependency_error_handler`→502, `_client_correctable_error_handler`→400, `_unhandled_error_handler`→500)을 `RoutingError`/`FilterIntentError`/`ReasoningError`×3/`SupervisorError`/`DiscoveryError`/`Exception`(catch-all) 각각에 등록했다. 500 핸들러는 서버 로그에는 `logger.exception()`으로 전체를 남기고 client에는 고정 메시지만 반환한다 — FastAPI의 기본 `RequestValidationError`(422)/`HTTPException` 처리는 더 구체적인 타입이 우선 매칭되어 그대로 유지됨을 실제 테스트로 확인했다.

## 12. OpenDART 다년(3개년) 재무 추세 (세션 3)

### 12.1 문제 인식

Stock Research Agent v1의 `investment_thesis`가 최근 한 해 수치를 나열하는 데 그치고, `risks`에도 비교 기준 없는 단일 PER/PBR/거래량 재진술이 섞이는 경우가 있었다 — 둘 다 "근거 있는 진짜 분석"이라기보다 단일 연도 수치의 재서술에 가까웠다.

### 12.2 실제 API 조사

새 인프라(반복 호출, 캐시)를 설계하기 전에 실제 OpenDART 응답부터 확인했다. 삼성전자(005930, corp_code=00126380, bsns_year=2025, reprt_code=11011)로 `fnlttSinglAcnt.json`을 직접 호출한 결과, 사업보고서(11011)는 **당기(thstrm)/전기(frmtrm)뿐 아니라 전전기(bfefrmtrm)까지 하나의 호출에 함께 내려준다**는 것을 확인했다(손익계산서/재무상태표 계정 모두 동일). 이 발견이 설계 전체를 결정했다 — 반복 호출이나 새 인프라 없이 기존 단일 호출을 재사용하는 것으로 충분하다.

### 12.3 설계 검토

15개 항목(3년 범위, report_code=11011 한정, 모델 최소 변경, deterministic 계산 범위, 흑자/적자 전환 정책, PER/PBR/ROE 생성 금지, catalyst/confidence 정책 불변, 신규 인프라 없음 등)을 제시했고, 사용자가 9개 항목을 그대로 승인하면서 `risks` 프롬프트 정책 한 가지를 완화해 반영해달라고 요청했다: "단일 수치는 risk가 될 수 없다"는 절대 금지가 아니라, **"비교 기준 없는 단일 시점 수치만으로 단정하지 않되, 다년 추세/전환 fact는 더 강한 근거로 쓸 수 있다"**는 형태로 규정 — deterministic fact와 risk 판단을 혼동하지 않는 것이 핵심이라는 취지였다.

## 13. Presentation Layer — `?view=detail|summary` (세션 4)

### 13.1 문제 인식

실제 Swagger에서 `POST /analysis`를 사용해보니 `portfolio_strategy` 응답이 보유 종목 수만큼의 `StockAnalysis`(investment_thesis/risks/catalysts/financial_history/evidence 전부 포함)를 담아 사람이 읽기 어려울 정도로 길었다. 그렇다고 `SupervisorResult`를 줄이면 향후 Web/Flutter 상세 조회와 machine-readable contract로서의 가치를 잃는다 — "기존 detail 유지 + 사람이 읽기 쉬운 요약 추가"가 목표였다.

### 13.2 설계 검토

13개 항목(presentation layer 필요 여부, deterministic vs LLM synthesis, intent별 shape, detail/summary 관계, Portfolio/Stock Research summary 구성, action 재판단 금지의 구조적 보장, summary text 필요 여부, API contract, payload size, Flutter 관점, 테스트 전략, v1/v2+ 범위)을 제시했고, 사용자가 전체 방향에 동의하면서 두 가지를 좁혀 확정했다:

1. **API view**: `view=both`는 v1에서 제외하고 `detail`/`summary` 두 가지만 구현. `view` 생략 시 기존 `SupervisorResult` 응답과 완전히 동일해야 함(기존 client 호환성).
2. **StockSummary 단순화**: `FinancialTrendPoint`/`financial_trend` raw history를 summary에 넣지 않음 — ANALYSIS-01(다년 재무 추세)로 `investment_thesis`가 이미 이 추세를 문장으로 설명하므로, summary에 숫자를 다시 넣으면 summary/detail 경계가 흐려진다는 이유였다.

### 13.3 구현

- `app/models/presentation.py`(신규): `MarketSummary`/`StockSummary`/`DiscoverySummary`/`RecommendationSummary`/`PortfolioSummary`/`PresentationResult`. `StockSummary`는 symbol/name/price/change_pct/investment_thesis/risks/catalysts/risk_level/confidence만 담고 financial_history/evidence/financials/scenarios는 없음. `RecommendationSummary`에는 target_weight/target_price 필드 자체가 없음. `DiscoverySummary.candidates`는 `Candidate` 모델을 그대로 재사용(이미 최소 구조라 별도 요약 모델 불필요).
- `app/api/presentation.py`(신규): `build_presentation(result: SupervisorResult) -> PresentationResult` — LLM/외부 API를 인자로 받지 않는 순수 함수. 기존 grounded 필드(각 Agent의 summary/investment_thesis/rationale)를 그대로 옮기거나 개수만 센다. 새 자유생성 LLM synthesis는 사용하지 않는다. `PORTFOLIO_STRATEGY`도 `stock_analyses`를 갖고 있지만(보유종목 fan-out 결과), `PresentationResult.stocks`는 그 경우 항상 빈 리스트로 둔다 — 종목별 상세는 `PortfolioSummary.recommendations`로만 노출해 원래 문제(응답 과다)가 요약에서 재현되지 않게 했다. `CANDIDATE_DISCOVERY`는 후보(`candidates`)와 그 fan-out 분석 요약(`stocks`)을 함께 노출한다.
- `app/api/routes.py`: `POST /analysis`에 `view: Literal["detail", "summary"] = "detail"` 쿼리 파라미터 추가. `response_model=SupervisorResult` 고정을 `response_model=None`으로 바꿔 view 값에 따라 `SupervisorResult`/`PresentationResult` 중 실제 반환된 객체를 그대로 직렬화하게 했다(Union 타입을 `response_model`에 직접 선언하면 두 모델이 공통으로 `intent` 필드를 가져 FastAPI/Pydantic의 smart union 재검증이 잘못된 멤버로 매칭될 위험이 있어 피했다). `view` 생략(또는 `detail`) 시 반환 객체가 기존과 동일한 `SupervisorResult` 인스턴스라 응답 shape이 100% 유지됨을 실제 `TestClient` 호출로 직접 확인했다.

detail/summary 두 호출은 서로 독립된 Supervisor 실행이라(market regime이 `neutral`/`risk_on`으로, recommendation_count가 6/10으로 서로 다르게 나옴) LLM reasoning 자체의 비결정성이 그대로 드러났다 — 이는 presentation layer와 무관한 기존 특성이며, presentation의 pass-through 정확성 자체는 `test_presentation.py`에서 같은 `SupervisorResult` 객체로 결정론적으로 검증했다.

## 15. 다음 세션 우선 검토: UX-04 (analysis snapshot lifecycle)

**아직 구현 방향을 확정하지 않았다.** 다음 세션은 여기서부터 설계 검토를 시작하고, 설계안을 제시한 뒤 반드시 사용자 승인을 기다린다.

### 15.1 문제를 정확히 정의

```text
POST /analysis?view=summary   → Supervisor 실행 #1 → PresentationResult
POST /analysis?view=detail    → Supervisor 실행 #2 → SupervisorResult
```

`view=summary`와 `view=detail`은 **같은 분석 결과를 다른 모양으로 보여주는 것이 아니라, 매번 Agent/LLM pipeline 전체를 독립적으로 재실행**한다. LLM reasoning은 결정론적이지 않으므로(Portfolio Strategy의 `recommendations` 개수와 action이 실제로 두 호출 사이에 달랐던 것을 §13.5에서 실측했다), 사용자가 summary 화면에서 본 판단과 detail 화면에서 보는 판단이 다를 수 있다. Flutter 시나리오로 구체화하면:

```text
summary 화면: "현대차 REDUCE"
  ↓ 사용자가 현대차 카드를 탭
detail 화면: Supervisor 재실행 → "현대차 HOLD"   ← 같은 종목인데 판단이 바뀜
```

추가로, `portfolio_strategy`처럼 비용/latency가 큰 요청을 detail 조회 한 번을 위해 통째로 재실행하는 것 자체가 비효율적이다.

### 15.2 핵심 검토 질문 (설계 검토 시 빠짐없이 다룰 것)

- 최초 `POST /analysis`가 `analysis_id`를 응답에 포함해야 하는가?
- `GET /analysis/{analysis_id}` 같은 별도 detail 조회 endpoint가 필요한가, 아니면 기존 `POST /analysis` 계약을 유지하는 다른 방법이 있는가?
- in-memory TTL cache 정도로 v1을 시작할 수 있는가?
- FastAPI single-process(`--workers 1`) 전제에서는 이 정도로 충분한가?
- uvicorn `--reload`나 프로세스 재시작 시 캐시된 분석 결과가 사라지는 것을 v1에서 허용할 것인가?
- multi-worker 배포로 확장하면 이 캐시는 어떤 한계에 부딪히는가(Kiwoom token 캐시가 워커별로 분리되는 것과 동일한 문제인지)?
- 지금 시점에 DB가 정말 필요한가, 아니면 더 가벼운 수단으로 충분한가?
- Redis는 아직 과설계인가?
- 같은 snapshot에서 summary/detail projection이 항상 일치함을 어떻게 보장할 것인가(`build_presentation()`이 순수 함수라는 §13의 전제를 그대로 활용할 수 있는가)?
- 기존 `POST /analysis`(view 생략 시 기존 응답 그대로)의 backward compatibility를 어떻게 유지할 것인가?

### 15.3 명시적 제약

## 16. Analysis Snapshot Lifecycle — UX-04 구현 (세션 5)

### 16.1 문제 인식

§13.5/§15에서 정의한 문제 그대로: `view=summary`와 `view=detail`을 각각 별도 `POST /analysis`로 요청하면 Supervisor/Agent/LLM pipeline이 매번 독립적으로 재실행된다. LLM reasoning은 비결정적이므로 실제 E2E에서 같은 portfolio 질문에 대해 recommendation 개수(6건 vs 10건)·market regime(`neutral` vs `risk_on`)이 두 호출 사이에 달랐다. 목표는 **한 번 실행된 `SupervisorResult`에 `analysis_id`를 부여하고, 이후 summary/detail 조회가 동일 snapshot을 공유하며 Supervisor/LLM/외부 API를 재실행하지 않는 것**이다.

### 16.2 설계 검토 및 확정된 v1 architecture

사용자가 이번 세션 시작 시점에 이미 구체적인 v1 architecture를 확정해 제시했다(§15의 질문 목록에 대한 답이 이미 포함됨):

- `POST /analysis`가 실행 후 결과를 `AnalysisSnapshotStore`에 저장하고 `analysis_id`를 발급, `X-Analysis-ID` response header로만 전달(body wrapper 신설 없음 — backward compatibility 유지).
- `GET /analysis/{analysis_id}?view=detail|summary` 신규 endpoint — snapshot 조회 전용, `Supervisor.run()`을 호출하지 않음.
- `analysis_id`는 Core model(`UserRequest`/`SupervisorResult`/`PresentationResult`)에 추가하지 않음 — API/snapshot lifecycle metadata와 투자 분석 domain data를 분리.
- Store는 in-memory TTL store(v1 기본 30분), DB/Redis/background job 없음. lock은 예방적으로 넣지 않되, `put()`/`get()`에 실제 `await` 지점이 있는지 확인 후 필요성을 판단.
- 없거나 만료된 id는 404(내부 정보 비노출 고정 메시지), 410은 사용하지 않음(store가 과거 존재 여부를 구분해 보관하지 않음).

repository 확인 결과(구현 전 검토):

- `app/api/main.py`의 `lifespan`이 `SupervisorOrchestrator`를 1회 생성해 `app.state.supervisor`에 저장하고 `routes.py`의 `get_supervisor(request)`가 이를 반환하는 기존 패턴이 그대로 재사용 가능함을 확인 — `AnalysisSnapshotStore`도 동일 패턴(`app.state.snapshot_store` + `get_snapshot_store(request)`)으로 얹었다.
- `POST /analysis`가 이미 `response_model=None`으로 `SupervisorResult | PresentationResult`를 직접 반환하고 있어, `Response` 파라미터를 주입받아 `response.headers["X-Analysis-ID"]`를 설정하는 것만으로 기존 body 직렬화 로직을 전혀 건드리지 않고 header를 추가할 수 있음을 확인했다.
- `main.py`의 기존 exception handler(`RoutingError`/`FilterIntentError`/`ReasoningError`×3 → 502, `SupervisorError`/`DiscoveryError` → 400, `Exception` → 500)가 `HTTPException`/`RequestValidationError`를 가리지 않는다는 것이 이미 테스트로 검증돼 있어(422 테스트), `GET /analysis/{id}`에서 없거나 만료된 snapshot에 `fastapi.HTTPException(404, ...)`을 그대로 raise해도 우리 catch-all 500 handler에 먹히지 않고 정확히 404로 응답됨을 확인했다.
- `app/config.py`는 API key류 env 설정만 담고 있고, `MAX_STOCK_RESEARCH_FANOUT`(discovery) 같은 정책 상수는 사용처 모듈에 상수로 두는 것이 이 repo의 기존 관례임을 확인 — TTL도 동일하게 `app/api/snapshot_store.py`의 모듈 상수(`DEFAULT_ANALYSIS_SNAPSHOT_TTL`)로 두고 config.py/환경변수에는 추가하지 않았다.
- repo 어디에도 `uuid` 사용 이력이 없어 명세대로 `uuid.uuid4()`를 채택했다.
- `test_kiwoom_service.py`의 만료 테스트가 "이미 만료된 값을 미리 채워 검증"하는 방식임을 확인했으나, TTL store는 "생성 후 시간 경과"를 시뮬레이션해야 해서 store 생성자에 `clock: Callable[[], datetime]`(기본값 `datetime.now(UTC)`)을 선택적으로 주입 가능하게 해 테스트에서 fake clock으로 결정론적으로 만료를 재현했다 — `sleep()` 미사용.

이견/충돌 없이 원안 그대로 진행했다.

### 16.3 구현

```text
app/api/snapshot_store.py     # 신규 — AnalysisSnapshotStore(uuid4 id, clock 주입 가능, lazy TTL eviction)
app/api/main.py                # lifespan에 app.state.snapshot_store 추가
app/api/routes.py              # get_snapshot_store(), POST /analysis에 X-Analysis-ID header,
                                # GET /analysis/{analysis_id}?view=detail|summary 신규
```

- `AnalysisSnapshotStore.put()`은 `uuid4()` 기반 `analysis_id`를 발급하기 전에 내부 dict를 순회해 만료된 항목을 함께 정리한다(별도 background cleanup task 없이, 쓰기 시점마다 정리해 "아무도 get()하지 않는 만료 id"로 인한 무한 누적을 방지). `get()`은 조회 시점에 만료 여부를 판정해 만료됐으면 그 항목만 즉시 evict하고 `None`을 반환한다.
- **Lock 미추가 판단**: `put()`/`get()` 모두 `await` 지점이 없는 순수 동기 dict 연산이다 — 이벤트 루프는 `await` 지점에서만 다른 코루틴으로 넘어가므로, 이 메서드들이 실행되는 동안 다른 요청이 끼어들 수 없다(atomic). race가 발생할 지점 자체가 없어 `asyncio.Lock`을 예방적으로 추가하지 않았다. 이 판단은 현재 `--workers 1` 단일 프로세스 전제에서만 유효하며, multi-worker로 확장하면(v1 범위 밖) 이 in-memory dict 자체가 worker마다 분리되는 더 근본적인 한계(Kiwoom access token 캐시와 동일한 성격)에 먼저 부딪힌다.
- `POST /analysis`: `Supervisor.run()` 직후 `snapshot_store.put(result)`로 `analysis_id`를 발급해 `response.headers["X-Analysis-ID"]`에 싣는다. `view` 분기(detail/summary body 결정) 로직은 기존 그대로 두어 body shape에 어떤 변경도 없다.
- `GET /analysis/{analysis_id}`: `snapshot_store.get(analysis_id)`가 `None`이면 `HTTPException(404, detail="Analysis snapshot not found or expired.")`. 있으면 `view`에 따라 저장된 `SupervisorResult`를 그대로 반환하거나 `build_presentation()`(순수 함수, §13에서 이미 구현됨)을 적용해 반환한다 — 이 경로에는 `Supervisor`/`LLMService`/`KiwoomService`/`OpenDartService`/`EcosService` 어느 것도 참조되지 않는다(코드 자체에 재실행 경로가 없음).

## 17. Candidate Discovery Theme Axis — UX-01 구현 (세션 6)

### 17.1 문제 인식과 사전 조사(같은 세션 앞부분, 코드 변경 전)

UX-04 완료 후 §14/§0.4 우선순위대로 UX-01을 다뤘다. 구현 전에 먼저 **"Kiwoom REST API가 실제로 제공하는 Industry/Theme taxonomy와 종목 membership을 실데이터로 검증"**하는 순수 조사 단계를 거쳤다(이 세션 앞부분, 코드 변경 없음 — 사용자가 명시적으로 "아직 구현하지 마세요"로 지시). 조사 결과 요약(자세한 원본 결과는 세션 로그 참고, 이 파일에는 구현에 반영된 결론만 남긴다):

- **가설이 틀렸다**: "`ka10101`(업종코드 리스트)이 `ka10099.upName`보다 세분화돼 있을 것"이라는 원래 가설을 실제 API 호출로 반증했다 — `ka10101`은 KOSPI 31개/KOSDAQ 34개의 굵직한 KRX 대분류였고, 삼성전자·SK하이닉스·LG에너지솔루션이 전부 "전기/전자" 하나에 뭉뚱그려짐을 `ka20002`(업종별주가요청)로 실제 멤버십을 조회해 확인했다.
- **Theme API(`ka90001`/`ka90002`)에 실제로 세분화된 정보가 존재**했다 — `ka90001(qry_tp=0)` 전체검색으로 142개 테마를 확인했고, 반도체(8개 세부 테마), 2차전지(2개), 로봇(1개), 원자력(2개, "원전"이 아니라 "원자력" 명칭) 등 실제 investment concept과 대응하는 테마가 다수 존재했다. 반면 AI/인공지능/데이터센터/HBM/자율주행은 `qry_tp=0` 전체 목록과 `qry_tp=1` 직접 검색 모두에서 전혀 매칭되지 않았다.
- **breadum/kiwoom은 실제로는 OCX(Windows COM, PyQt5 signal/slot) 기반 legacy wrapper**로, 이 프로젝트의 async REST 구조와 무관해 참고 가치가 낮았다. 실제 async REST reference는 sibling repo `breadum/kiwoom-restful`(4계층 Client/Socket/API/Bot, `request_until()` continuation 추상화, Client 계층 자동 rate limiting)이었으나, 우리 `KiwoomService.request()`의 기존 continuation 패턴(`cont_yn`/`next_key`)이 `ka20002`/`ka90001`/`ka90002`에도 그대로 잘 작동함을 실측 확인해 dependency로 추가하지 않았다(reference-only).
- 이 조사를 바탕으로 사용자가 **C안("Semantic Industry + Grounded Theme")**을 확정해 제시했다: Industry axis는 별도 API 연동 없이 기존 `upName`을 재사용하고, Theme axis(`ka90001`/`ka90002`)를 완전히 별도로 추가한다.

### 17.2 확정된 v1 구현 범위 (사용자 지시)

- **`ka10101`/`ka20002`는 이번 production path에 연동하지 않는다** — verified capability이지만 upName보다 세분화돼 있지 않아 실질적 가치가 없다.
- **`ka90001`/`ka90002`만 신규 연동**한다. Theme catalog(`ka90001`)는 `KiwoomService` instance에 캐시(TTL, financial validity 아님), membership(`ka90002`)은 요청된 테마만 lazy 조회(142개 전체 사전 구축 금지).
- **`DiscoveryFilter`에 `theme_requests` 신설**, 기존 `sector_terms`는 이름 변경 없이 그대로 유지(backward compatibility, Industry 의미로 재정의만).
- **Theme은 UNION(같은 concept 내), 서로 다른 axis는 INTERSECTION**.
- **Grounding은 Python이 최종 권한**: LLM이 "원전→원자력_*" 같은 동의어 normalization을 제안할 수 있지만 실제 카탈로그 존재 여부는 Python이 재검증하고, 지원하지 않는 concept은 `DiscoveryError`로 명시적으로 실패시킨다(조용한 narrowing 금지).
- **`Candidate.sector`/`matched_filters: dict[str, str]`는 변경하지 않는다** — public DTO는 단순하게 유지하고, 새 evidence는 `matched_filters`의 새 key(`theme`/`theme_concept`)로만 표현한다(`dict[str, Any]`로 느슨하게 넓히지 않음).

**Case 5 (AI unsupported) — 초기 실패, 프롬프트 수정으로 해결**:

- 최초 실행에서 "AI 관련주 찾아줘"가 **예상과 다르게 `DiscoveryError`(52건 초과)로 실패**했다. `classify()`를 직접 호출해 원인을 확인한 결과, 실제 LLM이 concept "AI"를 "로봇_지능형"/"클라우드 컴퓨팅"/"SI(시스템통합)"/"보안_인터넷"/"모바일솔루션" 5개 테마에 매칭시키고 있었다 — 이 테마명들은 전부 **실제 카탈로그에 존재하는 값**이라 구조적 grounding(Python의 `_validate()`)은 정상 통과했지만, "AI가 응용될 수 있는 산업"이라는 약한 연관성으로 매칭한 것이지 "AI 자체를 가리키는 테마"가 아니었다.
- 이는 이 프로젝트가 지켜온 "hallucination 방지"와는 다른 종류의 문제다 — **테마명 자체는 진짜(hallucination 아님)이지만, concept과의 의미적 대응이 지나치게 느슨했다.** grounding이 "존재하는 값인가"만 검증하고 "정말 그 개념을 가리키는가"는 검증할 수 없는 구조적 한계다.
- 해결: Python에 하드코딩된 alias/blocklist를 추가하는 대신(원칙 위반), **프롬프트 자체를 강화**했다 — "동의어 수준으로 대응할 때만 선택", "약한 연관성/응용 가능성만으로는 선택 금지", AI 사례를 부정 예시로 명시, "확신이 서지 않으면 포함하지 말라(과다 포함보다 누락이 안전)"는 원칙을 추가했다. 수정 후 재검증한 결과 "AI" → `matched_themes=[]`로 정상화됐고, `반도체`/`2차전지`/`로봇`/`원전` 등 기존에 올바르게 동작하던 concept들은 회귀 없이 그대로 동작함을 재확인했다.
- 전체 pipeline으로 재실행한 결과: "AI 관련주 찾아줘" → `DiscoveryError: 현재 지원하지 않는 테마 조건입니다: AI.` — Case 5 요구사항대로 명시적·결정론적 실패를 확인했다.

**부수 발견 — 다중 concept 분리**: "AI 반도체 관련주 찾아줘"를 테스트하는 과정에서, LLM이 두 단어를 **하나의 합성 concept("AI 반도체")로 묶어** "반도체_시스템반도체" 하나에만 매칭시키는 경우를 발견했다 — 결과적으로 "AI"가 unsupported로 잡히지 않고 조용히 통과되어, 이 프로젝트가 명시적으로 금지한 "일부 concept만으로 조용히 좁혀서 답하는" 상황이 다른 경로로 재현될 뻔했다. 프롬프트에 "A와 B처럼 명확히 나열된 서로 다른 개념은 분리하되, 그 자체로 하나의 고유한 대상을 가리키는 게 명백한 합성어(예: AI 전용 반도체)라면 유지해도 된다"는 지침을 추가해, "AI와 반도체"/"AI 반도체" 모두 `concept="AI"`(빈 매칭)와 `concept="반도체"`(8개 매칭)로 정확히 분리됨을 재확인했다. 이 케이스는 §19의 필수 E2E 항목은 아니었지만, 실제 LLM 검증 과정에서 발견해 함께 수정했다.

**Case 6 (2차전지, coverage gap 확인)**: "2차전지 관련주 찾아줘" → 2차전지_완제품(3: SK이노베이션/LG화학/삼성SDI) + 2차전지_소재(14) = 17종목 → fan-out 한도 초과로 `DiscoveryError`. 17 = 3+14로 겹침이 없어 두 테마의 union이 정확히 계산됨을 확인했고, 특히 **LG에너지솔루션(373220)이 어떤 2차전지 테마에도 속하지 않는다는 사전 조사 결과(스핀오프 이전 구조를 반영하는 것으로 추정)가 그대로 재현**됨을 확인했다 — 이 gap은 코드로 보정하지 않고 아래 UX-05로 기록했다.

**부수 발견 — 실제 429 rate limit 관측**: Case 2/3 검증 과정에서 짧은 시간에 여러 `ka90002` 호출이 이어지자 실제로 `httpx.HTTPStatusError: Client error '429 null'`이 발생했다(약 20초 후 재시도는 여전히 429, 90초 후 재시도는 성공). 이전 세션(dev-log 2026-08-28 §3)에서는 `ka10099` 응답 헤더에 rate-limit 정보가 없어 "미확인"으로 남겼는데, **이번에 처음으로 실제 429를 관측**했다 — 다만 여전히 응답 헤더에는 rate-limit 관련 정보가 없어 정확한 한도(초당/분당 몇 회)는 확인하지 못했다. 이번 UX-01 범위에서는 retry/backoff를 추가하지 않았다(요청 범위 밖) — PERF-01과 마찬가지로 별도 최적화 과제로 남긴다.

### 17.9 Final Hardening (§17 승인 이후, 같은 세션)

사용자가 architecture/기능을 승인하면서 commit 전 3가지 hardening을 지시했다. 범위를 넓히지 않고 아래만 처리했다.

**1) Theme grounding responsibility 재검토 — 실제로 변경함.**

기존 구조(`LLM이 matched_themes 직접 선택 → Python이 존재 여부만 검증`)는 hallucination(카탈로그에 없는 이름)은 막았지만, §17.5에서 실측된 "AI가 클라우드컴퓨팅/보안_인터넷처럼 **실제로 존재하는 무관한 테마**에 과다 매칭되는" 문제는 구조적으로 막지 못했다 — 프롬프트 문구만으로 막았던 것이라 재발 가능성이 있었다.

Before/After:

```text
Before
  LLM: concept + matched_themes(카탈로그 전체 중 직접 선택)
  Python: matched_themes ⊆ known_themes만 검증(존재 여부)
  → 존재하지만 무관한 테마 선택은 못 막음(AI 사례로 실측)

After
  LLM: concept + normalized_concepts(자유 제안, 카탈로그 안 봄)
  Python: _match_theme_names([concept, *normalized_concepts], known_themes)
          — exact 또는 "{term}_" prefix만 인정하는 순수 문자열 매칭
  → LLM은 "무엇을 고를지" 자체를 결정할 권한이 없음. 최종 matched_themes는
    항상 known_themes의 부분집합이도록 구조적으로 보장됨(검증이 아니라
    애초에 그 외의 값이 나올 경로가 없음)
```

구현: `app/discovery/filter_intent.py`에 `_RawThemeRequest(concept, normalized_concepts)`(LLM 응답 파싱 전용)와 `_match_theme_names()`(순수 함수, exact/prefix만) 추가. `ThemeRequest(concept, matched_themes)` 공개 모델과 orchestrator.py 소비 코드는 전혀 바꾸지 않았다 — `_parse_response()` 내부에서만 책임이 이동했다. `_validate()`의 theme 관련 검증은 제거했다(더 이상 필요 없음 — hallucination이 구조적으로 불가능해짐). 프롬프트도 "카탈로그에서 정확히 골라라"는 지시에서 "동의어를 자유롭게 제안해라(틀려도 시스템이 걸러낸다)"로 단순화됐고, 142개 테마명을 매 요청 프롬프트에 렌더링하던 부분도 제거했다(더 이상 LLM이 볼 필요 없음 — 토큰 비용도 함께 줄었다).

검증: `2026-08-28 UX-01 조사`에서 실측한 Kiwoom 테마 카탈로그가 "카테고리_세부항목"(예: `반도체_생산`, `2차전지_완제품`, `원자력_기자재`) 명명 규칙을 실제로 쓰고 있어, `반도체`/`2차전지`/`로봇` 같은 concept은 **정규화 없이 concept 자체가 prefix로 직접 매칭**되고, `원전`처럼 어휘 자체가 다른 경우만 LLM의 `normalized_concepts`(예: "원자력") 제안에 의존한다. 범용 synonym dictionary(하드코딩)나 fuzzy semantic engine은 만들지 않았다 — 매칭 규칙은 정확히 두 가지(exact, prefix)뿐이다.

**2) 실제 429 관측 경로 확인 — 최소 pacing 추가, retry/backoff는 추가하지 않음.**

`KiwoomService.request()`에는 애초에 retry/backoff/rate control이 전혀 없다(단일 HTTP POST + `raise_for_status()`뿐). `_resolve_theme_membership()`의 `get_theme_stocks()` 호출은 이미 **순차적**이었다(concurrent가 아님, `asyncio.gather` 등 없음) — 그런데도 429가 발생한 것은 순차 호출 사이에 지연이 전혀 없어서였다("반도체"처럼 8개 세부 테마가 매칭되면 8회 연속 즉시 호출).

Kiwoom 공식 REST API 예제 저장소(`Kiwoom-Securities/Kiwoom-REST-API`)의 `ka90001`/`ka90002` 예제 코드 자체가 연속조회 페이지 사이에 `REQUEST_DELAY_SECONDS = 0.2`를 이미 쓰고 있음을 2026-08-28 세션 초반 조사에서 확인한 바 있어, 동일한 값을 그대로 채택했다 — `_resolve_theme_membership()`이 **서로 다른 테마를 연속 조회할 때만**(같은 요청 안에서, 첫 호출 전에는 대기하지 않음) `asyncio.sleep(0.2)`를 둔다. generic rate-limit framework, global scheduler, queue, background worker는 만들지 않았고, 정확한 Kiwoom 호출 한도는 여전히 추측하지 않는다.

**의도적으로 하지 않은 것**: retry/backoff. 이 지연은 429 발생 자체를 막는 보장이 아니라 발생 확률을 낮추는 완화책일 뿐이다 — 429가 실제로 나면 이 v1은 여전히 `httpx.HTTPStatusError`를 그대로 전파한다(catch하지 않음). 이유: 정확한 rate limit을 모르는 상태에서 retry 횟수/backoff 곡선을 설계하는 것 자체가 추측에 근거하게 되고, "generic rate-limit framework를 만들지 마라"는 명시적 제약과 충돌할 위험이 있다고 판단했다. 이 잔여 위험은 아래 Known Issue로 남긴다.

**3) Theme catalog TTL 문서화 — 코드/README 주석 보강, 값 자체와 구조는 변경 없음.**

`THEME_CATALOG_CACHE_TTL = timedelta(hours=24)`은 그대로 유지했다. `app/services/kiwoom.py`의 상수 주석과 README "Candidate Discovery" 섹션에 다음을 명시적으로 추가했다: (a) financial validity 의미가 아니라는 것, (b) 실제 Kiwoom 테마 개편 주기를 관측하지 못했다는 것, (c) 24시간은 확정 사양이 아니라 현재의 잠정적 operational refresh 정책이라는 것, (d) 향후 실제 개편 주기가 관측되면 조정 가능하다는 것. 별도 configuration화(환경변수 등)는 하지 않았다 — 요청받지 않았고 지금은 과설계다.

**테스트**: `app/discovery/filter_intent.py`의 UX-01 관련 테스트를 새 계약(`normalized_concepts`)에 맞춰 재작성했고, `_match_theme_names()` 자체에 대한 순수 함수 단위 테스트 6건(prefix/exact/no-match/fallback/first-match-wins/근거없는 제안의 무해성)을 추가했다. `test_discovery_orchestrator.py`도 fake LLM 응답의 필드명만 `normalized_concepts`로 갱신했고(fake 테마 카탈로그가 이미 "concept_세부항목" 명명이라 대부분 정규화 없이 그대로 통과), 원전→원자력 정상화 경로를 orchestrator 레벨에서도 별도로 검증하는 테스트를 1건 추가했다. `_resolve_theme_membership()`에 추가된 `asyncio.sleep`은 fake 환경에서도 실제로 실행되므로(테마 2개 이상인 테스트 1건에 한해) 테스트 스위트에 약 0.2초의 실제 지연이 생겼다 — 무시할 만한 수준이다.
