### H.3 Ownership Alternatives

- **Option A — Evaluator-owned**: feature semantics와 가깝고 Protocol이
  허용한다. 그러나 (1) evaluator가 PolicyConfig(calibrated parameter)에
  의존하게 돼 §24.2 2.10 분리를 깨고, parameter 변경이 `evaluator_version`
  변경과 섞인다(semantic version ≠ policy version). (2) peer/market-relative
  normalization은 cross-sectional reference가 필요한데 `evaluate(data, context)`
  는 단일 종목 입력이다 — Protocol 확장 필요. (3) 같은 normalization mechanism이
  evaluator마다 중복된다. (4) FROZEN된 "evaluator는 directionality를 해석하지
  않는다" 경계와 충돌한다. → **REJECT**
- **Option B — Separate Feature Normalization stage**: evaluator 결과 +
  registry metadata + PolicyConfig + (필요 시) basis reference를 받아
  `normalized_value`를 채운 결과를 만든다. 새 model 불필요 —
  `FeatureEvaluationResult`가 이미 raw/derived/normalized slot을 분리한다
  (§30, `test_feature_evaluation_result_separates_raw_and_normalized_value`).
  입력 결과를 mutate하지 않고 새 인스턴스로 rebuild한다. 기존 evaluator
  test(normalized/directionality `None`)는 **evaluator 출력**에 대해 계속 참이다.
  orchestrator에 한 단계가 늘지만 orchestrator의 기존 역할(정해진 순서로 building
  block 호출)과 맞는다. → **SUPPORTED**
- **Option C — Assembly-owned**: Assembly의 FROZEN "조립만" 책임(§47/§48)과
  정면 충돌하고, feature-specific semantics가 aggregation layer로 샌다.
  → **REJECT**
- **Option D — Policy/Config-driven service**: B와 다른 책임 모델이 없다 — B
  stage가 곧 PolicyConfig를 소비하는 deterministic 단계다. → B로 **병합**
- **Option E — Hybrid (evaluator: semantic/direction, normalizer: scaling)**:
  "semantic transformation"은 B(derivation, owner는 별도 contract)의 몫이고,
  direction은 evaluator가 해석하지 않는 registry metadata다 — 나눌 근거가 되는
  별도 invariant가 없다. 실제로 존재하는 분리는 `derivation ≠ feature
  normalization`이고 이는 Option B 자체다. → **REJECT**(독립 option으로서)

### H.9 Evaluation Basis Contract (rev.1)

**이번 contract가 정하는 invariant**:

```text
- Normalization stage는 적용할 basis를 명시적으로 알아야 한다
  (묵시적 basis 없음 — 선택 주체는 PolicyConfig).
- 허용되지 않은(undeclared / unsupported) basis를 조용히 적용하지 않는다.
- relative basis의 reference data가 없다고 다른 basis로 silent fallback하지
  않는다 (fallback은 PolicyConfig가 명시할 때만).
```

**Current implementation fact vs future canonical semantics (구분)**:

- *current implementation fact*: 6개 evaluator가 `FeatureEvaluationResult
  .evaluation_basis = [ABSOLUTE]`를 출력하고 4개 test가 이를 고정한다. 이
  contract는 이 출력과 test를 바꾸지 않는다.
- *future canonical semantics*: 이 field가 "적용 가능 basis 선언"인지, "raw
  측정 basis"인지, "적용된 basis 기록"인지는 **정하지 않는다** — 현재 출력
  사실만으로 영구 의미를 부여할 evidence가 부족하다(§24.2 2.6은 "각 Feature에는
  적용 가능한 basis를 선언한다"고만 하며 선언 위치를 정하지 않았다).

**OPEN**: applicable-basis canonical declaration owner(registry vs evaluator vs
PolicyConfig), `evaluation_basis`의 최종 canonical semantics, multi-basis
representation(absolute + peer 결합 시 단일 slot 충분성 포함), peer 구성/peer

### H.10 Missing / Invalid / N/A / Zero / Negative

| availability / 값 | normalized_value | 근거 |
|---|---|---|
| `UNAVAILABLE` | `None` | `UNAVAILABLE ≠ 0`, missing ≠ neutral |
| `INVALID` | `None` | `INVALID ≠ NEGATIVE` — invalid 값을 수치로 표현하지 않음 |
| `NOT_APPLICABLE` | `None`, aggregation에서도 missing/zero로 취급하지 않음 | `NOT_APPLICABLE ≠ UNAVAILABLE`, coverage `not_applicable` bucket과 일치 |
| `AVAILABLE` 0 | policy가 있으면 정상 normalization 대상 | 0은 missing이 아니다 |
| `AVAILABLE` 음수(예: 음의 PER) | policy가 정의한 method로만 처리, INVALID로 재분류 금지 | Step D/E FROZEN(음수는 AVAILABLE raw evidence) |
| `ESTIMATED` | 구조적으로 normalization 가능. ESTIMATED 여부는 보존(`ESTIMATED ≠ observed`). 허용 여부는 PolicyConfig | §2.8 |
| policy 없음 / method 미정의 / basis 미지정 / reference 부재 | `None` + warning | no implicit default, no silent fallback |

**Normalization은 availability를 절대 바꾸지 않는다** → Coverage 결과에 영향이
없다. `UNKNOWN`은 availability 값이 아니며 이 layer에서 새로 만들지 않는다.

### H.11 Derived Feature Relationship (rev.1)

```text
derivation ≠ feature normalization
```

- Feature Normalization stage는 derived value를 **계산하지 않는다**.

stronger evidence 확인 결과: §32.6(`FROZEN candidate`)은 evaluator 책임 목록에
"deterministic feature derivation"을 포함해 evaluator derivation을 **허용**하지만

### S.2 Implementation (source/tests)

- `app/models/evidence.py`(신규): EvidenceSource / EvidenceOrigin / ObservationIdentity /
  DerivationLineage / EvidenceItemIdentity(frozen, semantic only) / EvidenceReference /
  FinancialFactsEvidence(6 slot). validator: SOURCE_REPORTED(source 필수, derivation 없음, tz-aware
  retrieved_at, input_references 없음), DERIVED(source 없음, derivation·inputs 필수, retrieved_at None,
  input_references identity == derivation.inputs).
- service: internal `fetch_financial_accounts` / `fetch_stock_info`가 성공 응답 직후 retrieved_at을
  기록, 공개 메서드는 위임(공개 signature / return model 불변).
- tool: internal `get_key_financials_history_with_evidence` / `get_stock_info_with_evidence`. OpenDART
  reference는 `_find_amount`와 같은 `_find_account` / measure 표로 고른 row에서 생성(rcept_no /
  reprt_code / fs_div / sj_div / source term / period notation / period label / retrieved_at),
  comparative는 나중 filing의 rcept_no + source term 유지. Kiwoom ROE / PER / PBR은 SOURCE_REPORTED,
  version anchor·formula lineage 없음.
- `analyze(..., evidence=None)`(optional kw, 기존 호출 불변) → derived reference(operating_margin /
  net_margin / debt_ratio, formula_version "1") → `DeterministicAnalysisResult.evidence`(optional; v1
  경로 불사용) → builder는 None이면 fail-fast → `FinancialFacts.evidence`(required, 값-evidence 정합
  validator) → 6개 evaluator가 `Provenance.evidence`에 reference 1개, derived는
  `FeatureValue.is_derived=True`(raw slot 유지).
- 설계 대비 배치 변경 1건: 값-evidence 완결성 검사를 builder 대신 `FinancialFacts` model validator에
  둔다 — builder source에 feature 이름이 없어야 한다는 기존 test(재계산 금지 guard)를 약화하지 않기
  위함. 검사 의미는 동일하며 NRD 생성 어디서나 강제된다.
- tests: 신규 `tests/test_evidence_identity_preservation.py`(15), test 전용 `tests/evidence_fixtures.py`
  (hand-built fixture용 evidence), 기존 pipeline fixture 18곳 wrap + 빈 `FinancialFactsEvidence()` 3곳.
  기존 assertion 변경 없음.
- 불변: `app/mcp/server.py`, 공개 model(OpenDartFinancialAccount / KeyFinancials / KiwoomStockInfo /
  CompanyFinancials), `app/models/stock.py`(StockAnalysis 등), stock-research orchestrator, v1 LLM 경로.
