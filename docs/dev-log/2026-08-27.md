## 2. 아키텍처 사전 검토

구현에 들어가기 전, 다음 4가지를 먼저 검토하고 합의했다(이번 로그에서는 결론만 기록한다. 상세 논의는 세션 대화 기록 참고).

### 2.1 Stock Research Agent는 PortfolioContext를 쓰지 않는다

종목 자체의 분석("이 종목이 투자 대상으로서 어떤가")과 사용자별 판단("나는 이 종목을 사야 하는가")을 분리했다. 후자는 Portfolio Strategy Agent의 책임으로 남긴다. 덕분에 `StockAnalysis`는 사용자·보유 여부와 무관하게 재사용 가능하고, Recommendation Engine이 미보유 종목까지 스캔할 때도 자연스럽다.

### 2.2 Agent는 MCP Client가 아니라 Domain Tool을 직접 호출한다

같은 프로세스 안에서 `KiwoomTools`/`OpenDartTools`를 직접 import해서 쓴다. MCP 프로토콜 왕복(직렬화 → dict → 재검증)은 프로세스 경계를 넘는 외부 클라이언트가 필요할 때만 의미가 있고, 지금은 그런 경계가 없다. MCP Server는 계속 살아있지만 "외부 노출 경계"라는 별도 역할로 재정의했다. README의 "MCP Client / Server Relationship" 섹션도 이 결정에 맞춰 갱신했다.

### 2.3 LLM reasoning의 layer 책임 분리

```text
Service (LLMService)     → raw OpenAI 호출만, prompt/reasoning 모름
Agent/analysis.py         → deterministic 계산, LLM 모름
Agent/reasoning.py         → LLM 호출 + 구조화 검증 + 최소 재시도
Agent/orchestrator.py      → 위 둘을 조합, confidence/risk_level 최종 강제
```

숫자(가격·재무)는 항상 deterministic layer에서만 나오고 LLM은 그 숫자에 대한 해석·서술만 담당한다는 원칙을 이때 세웠다.

### 2.4 공통 abstraction은 최소로

`BaseAgent`, 공통 reasoning interface, tool 호출 추상화 모두 지금은 만들지 않기로 했다. Agent가 하나뿐인 상태에서 "공통"을 추출하는 것은 근거 없는 예측이기 때문이다. 대신:

- `LLMService`(Service 레이어, 기존 Ecos/OpenDart/Kiwoom Service와 동일 패턴)만 지금 만든다.
- `analysis.py`/`reasoning.py` 내부의 작은 Pydantic 모델(`DeterministicFact`, `DeterministicAnalysisResult`, `ReasoningResult`)은 필요한 만큼만 만들고 `app/models/`에는 넣지 않는다(cross-cutting contract가 아니라 Agent 내부 작업 데이터이므로).

## 4. LLMService — `app/services/llm.py`

```python
class LLMResponse(BaseModel):
    content: str
    model: str
    finish_reason: str | None = None

class LLMService:
    def __init__(self, api_key: str, model: str, timeout: float = 30.0): ...
    async def complete(
        self,
```

결정 사항:

- **OpenAI 공식 SDK를 쓰지 않고 `httpx`로 REST를 직접 호출**했다. `pyproject.toml`에 `openai` 의존성이 없고, `EcosService`/`OpenDartService`/`KiwoomService` 모두 벤더 SDK 없이 `httpx` 직접 호출 패턴을 이미 확립해뒀기 때문에 그대로 따랐다.

테스트는 `httpx.MockTransport` 기반(기존 ECOS/Kiwoom 테스트와 동일한 mocking 방식)이며 API key 없이도 전부 통과한다.

## 5. Deterministic Analysis — `app/agents/stock_research/analysis.py`

### 5.1 최초 구현

```python
def analyze(stock_info: KiwoomStockInfo, key_financials: KeyFinancials) -> DeterministicAnalysisResult:
    ...
```

- `StockPriceSnapshot`/`FinancialSnapshot` 매핑 (손실 없이).
- Deterministic fact 2종: 250거래일 가격 위치, 부채비율.
- `max_confidence`: 핵심 재무 3종(매출/영업이익/순이익) 모두 있으면 MEDIUM, 아니면 LOW. **v1은 HIGH를 절대 반환하지 않는다**(공시·뉴스 같은 질적 근거가 없기 때문).
- `risk_level`: 최초에는 부채비율 임계값(≤100% LOW, ≥200% HIGH)으로 분기했으나, 이후 **제거**했다(5.2 참고).

### 5.2 risk_level 규칙 철회

부채비율 하나만으로 종목 전체의 투자 RiskLevel을 LOW/HIGH로 단정하는 것은 근거가 약하고 업종별 자본구조 차이도 반영하지 못한다는 판단에 따라, `_risk_level()`을 인자 없이 항상 `RiskLevel.MEDIUM`을 반환하도록 단순화했다.

```python
def _risk_level() -> RiskLevel:
    # v1은 가격 + 단일연도 재무 데이터만으로 종목 전체의 투자 RiskLevel을
    # LOW/HIGH로 판단하지 않는다. 업종 상대기준과 충분한 risk 데이터가
    # 확보된 뒤 별도 risk model로 확장할 예정이다.
    return RiskLevel.MEDIUM
```

부채비율 자체(수치)는 `DeterministicFact`로 계속 남겨 reasoning 단계의 `risks` 서술 근거로만 쓰이게 했다. **판단(risk_level)과 근거(fact)를 분리**한 것이 핵심이다.

### 5.3 Raw value fact 10종 추가

실제 E2E 데모를 처음 돌려보고 나서, reasoning이 참조할 수 있는 "평가 없는 원본 수치"가 가격위치·부채비율 2개뿐이라는 게 부족하다고 판단해 다음 10개를 추가했다.

```text
current_price, PER, PBR, ROE                         (Kiwoom)
revenue, operating_profit, net_income,
total_assets, total_liabilities, total_equity          (OpenDART)
```

원칙: **"PER가 높다" 같은 평가는 절대 하지 않고 원본 값만 담는다.** `_format_raw_value()`는 값의 크기와 무관하게 그대로 포맷팅만 한다. `test_raw_value_facts_contain_no_evaluative_language`로 "높다/낮다/양호/부진/고평가/저평가" 등 평가어가 fact에 섞이지 않는지 회귀 테스트를 걸었다.

이때 `high_250d`/`low_250d` 관련 fact 문구도 "52주" → **"250거래일"**로 정정했다. Kiwoom 필드가 실제로는 250거래일 기준이라 "52주"는 데이터 정의와 정확히 일치하지 않았다.

## 6. LLM Reasoning — `app/agents/stock_research/reasoning.py`

### 6.1 최초 구현

```python
class ReasoningResult(BaseModel):
    investment_thesis: str = Field(min_length=1)
    catalysts: list[str] = Field(default_factory=list)
    risks: list[str] = Field(default_factory=list)
    scenarios: list[StockScenario] = Field(default_factory=list)
    suggested_confidence: AnalysisConfidence
```

- `scenarios`는 새 모델을 만들지 않고 기존 `StockScenario`(bull/base/bear, target_price, probability 0~1)를 재사용했다.
- `generate_reasoning()`은 `analysis.py`가 만든 facts만 prompt에 넣고, JSON 구조화 출력(`response_format={"type": "json_object"}`)을 요청한 뒤 Pydantic으로 검증한다.
- 검증 실패 시 최대 2회까지 동일 prompt로 재시도하고, 모두 실패하면 **`ReasoningError`를 raise**한다 — fallback으로 근거 없는 값을 채우지 않는다.

### 6.2 실제 E2E에서 발견한 문제 1 — 임의의 target_price/probability

첫 실제 실행(삼성전자)에서 LLM이 bull/base/bear 시나리오에 각각 374,500원/261,500원/67,500원이라는 target_price를 붙여 반환했다. 이 숫자들은 사실 52주(250거래일) 최고가/현재가/최저가를 그대로 재사용한 것으로, **밸류에이션 근거 없이 만들어진 숫자**였다.

수정: prompt에 "v1에는 목표주가 산정 근거가 없다, target_price/probability는 항상 null"이라고 명시하고, **파싱 직후 Python이 무조건 제거**하는 구조적 안전장치를 추가했다.

```python
def _strip_unsupported_projections(result: ReasoningResult) -> ReasoningResult:
    # 프롬프트로 지시해도 LLM이 숫자를 만들어낼 수 있으므로
    # 여기서 항상 제거해 근거 없는 숫자가 절대 결과에 남지 않게 한다.
    sanitized_scenarios = [
        scenario.model_copy(update={"target_price": None, "probability": None})
        for scenario in result.scenarios
    ]
    return result.model_copy(update={"scenarios": sanitized_scenarios})
```

재시도가 아니라 **무조건 제거**를 택했다 — 재시도해도 다음 응답에서 다시 숫자를 만들 수 있어 신뢰할 수 없지만, Python이 지우면 100% 보장된다. `thesis` 서술 자체는 유지된다.

### 6.3 실제 E2E에서 발견한 문제 2 — 근거 없는 valuation 평가

PER/PBR/ROE에 대해 업종/과거 비교 데이터를 전혀 주지 않았는데도 LLM이 "높다/낮다/고평가" 같은 평가를 시도할 여지가 있었다.

수정: prompt에 "PER, PBR, ROE 등 비율 지표에는 비교 기준(benchmark)이 제공되지 않았다. 그런 지표는 수치 사실만 언급하라"는 문단을 추가했다.

### 6.4 실제 E2E에서 발견한 문제 3 — catalyst 의미 오염

가장 흥미로웠던 문제. 근거 없이 만들지 말라는 지시를 충실히 지키다 보니, LLM이 "매출액 333조원", "자산총계 566조원" 같은 **정적 재무 규모를 그대로 catalyst로 재진술**했다. 지어내지는 않았지만(요구사항은 지켰지만) catalyst라는 라벨의 의미와 맞지 않았다.

수정: catalyst를 별도 문단으로 분리하고 정의를 좁혔다.

```text
catalysts는 향후 주가·실적·기업가치에 영향을 줄 수 있는 구체적인
변화나 이벤트만을 의미한다. 다음은 그 자체로는 catalyst가 아니다:
- 단순 매출 규모
- 단순 순이익 규모
- 자산/자본 규모
- PER/PBR/ROE 수치
- 부채비율
- 현재 가격 위치
주어진 facts 안에 이런 미래 지향적 이벤트/변화의 근거가 없다면
catalysts는 반드시 빈 리스트 []를 반환한다.
```

target_price/probability와 달리 catalyst는 **자연어 문자열**이라 "이게 진짜 이벤트인지, 규모 재진술인지"를 Python이 기계적으로 검증할 수 없다. 이 부분은 prompt 정의를 좁히는 것으로만 대응했고, 실제로 잘 지켜지는지는 다시 데모로 확인했다(8절).

### 6.5 scenarios=[] 허용

기존에는 scenarios를 빈 배열로 반환해도 되는지 prompt에 명시하지 않았다. "현재 데이터만으로 서로 구분되는 시나리오를 정당화할 수 없다면 scenarios=[]를 반환해도 된다"는 문장을 추가해 억지 시나리오 생성을 막았다.

## 7. Orchestrator — `app/agents/stock_research/orchestrator.py`

```text
stock_code
   │
   ├─► KiwoomTools.get_stock_info()
   ├─► OpenDartTools.get_key_financials()
   │
   ▼
analysis.analyze()  →  DeterministicAnalysisResult
   │
   ▼
generate_reasoning()  →  ReasoningResult
   │
   ▼
StockAnalysis 조립
```

최종 조립 시 강제한 정책 3가지:

1. **confidence = min(reasoning_result.suggested_confidence, analysis_result.max_confidence)**
   `AnalysisConfidence`는 문자열 Enum이라 자체 순서 비교가 안 되므로 LOW=0/MEDIUM=1/HIGH=2 랭킹 맵을 별도로 뒀다. LLM이 아무리 자신 있게 답해도 데이터가 부족하면 Python이 낮춘다. 반대로 LLM이 스스로 더 낮게 제안하면 그 값을 존중한다(양방향 테스트로 확인).

2. **risk_level은 `analysis_result.risk_level`만 사용.** `ReasoningResult`에는 애초에 `risk_level` 필드가 없어 LLM이 관여할 방법이 구조적으로 없다.

3. **evidence는 `analysis_result.facts` + 실제 tool 호출 출처(2건)로만 구성.** `reasoning_result`는 `_build_evidence()`에 아예 전달되지 않아 LLM이 evidence를 만들 통로가 없다.

4. **`ReasoningError`는 삼키지 않고 그대로 전파.** fallback `StockAnalysis`를 만들지 않는다 — "근거 없는 결과보다는 실패를 알리는 쪽"을 택했다.

이번 단계에서 `analysis.py`에 `risk_level` 필드가 없었다는 걸 뒤늦게 발견해(직전 단계 범위 밖이라 빠져 있었음) `analysis.py`에 최소한으로 보완하고 넘어갔다.

## 8. 실제 E2E 검증 — 삼성전자(005930)

`scripts/stock_research_demo.py`로 실제 Kiwoom/OpenDART/OpenAI(gpt-5-mini) API를 호출해 세 차례 실행했다.

### 1차 실행 (reasoning 최초 구현 직후)

문제 발견:

- `catalysts`에 매출/순이익/자산 규모 5개가 그대로 재진술됨 → 6.4에서 수정 예정으로 확인.

### 2차 실행 (target_price/probability 강제 제거 + valuation 평가 금지 적용 후)

### 3차 실행 (catalyst 정의 강화 후, 최종)

```text
risk_level : medium
confidence : medium

Catalysts:
(없음)

Risks:
- PER 39.84배 관련 밸류에이션 노출
- 부채비율 약 29.9% 관련 재무구조 노출
- 250거래일 63.2% 위치 관련 가격 변동 노출

Scenarios:
(없음)

Evidence: 14건 (deterministic fact 12건 + tool 호출 출처 2건)
```

- `catalysts: []` — 이벤트성 근거가 전혀 없는 v1 데이터 구성상 정상적인 결과.
- `risks`는 여전히 채워지되, 동일한 raw fact(PER/부채비율/가격위치)를 "평가"가 아니라 "노출(exposure)" 서술로만 다룸.
- target_price/probability, 임의 catalyst 모두 재현되지 않음.

세 번의 실행을 거쳐 최종적으로 "근거가 없으면 생성하지 않는다"는 원칙이 실제 LLM 출력에서도 안정적으로 지켜지는 것을 확인했다.

## 9. "근거가 없으면 생성하지 않는다" 원칙 정리

오늘 구현 전반에 적용한 원칙을 layer별로 정리하면:

```text
Model Layer
    optional 필드 + 기본값 None
    → 값이 없으면 없다고 명시적으로 표현, 임의 채움 없음

analysis.py (deterministic)
    fact 생성 조건이 불충족하면 조용히 생략 (None 반환 → 리스트에서 제외)
    raw value fact는 평가 없이 수치만

reasoning.py (LLM)
    prompt: 주어진 facts 밖의 정보 추측 금지
    prompt: 비교 기준 없는 지표 평가 금지
    prompt: catalyst는 이벤트성 근거만, 정적 규모 재진술 제외
    prompt + 후처리: target_price/probability는 항상 null
    빈 catalysts/risks/scenarios를 정상 출력으로 허용 (억지로 채우지 않음)
    구조화 검증 실패 시 재시도, 최종 실패 시 명시적 예외(ReasoningError)

orchestrator.py
    confidence: LLM 제안값과 deterministic 상한 중 더 낮은 값 강제
    risk_level: deterministic 결과만 사용, LLM이 변경 불가
    evidence: deterministic facts + 실제 tool 호출 출처로만 구성
    ReasoningError 발생 시 fallback 없이 예외 전파
```

숫자(가격/재무/target_price)는 Python이 구조적으로 보장하고, 텍스트(catalyst 의미 등)는 prompt 정의로 최대한 좁히되 완벽한 기계적 보장은 불가능하다는 점을 이번 구현에서 명확히 확인했다.

## 13. Market Agent v1 구현 (세션 2)

### 13.1 설계 검토 먼저 진행

구현 전에 코드 수정 없이 설계안부터 검토했다. Stock Research Agent v1의 코드(`app/agents/stock_research/`)와 README, 기존 `MarketAnalysis`/`MarketIndicator` 모델을 근거로 다음을 확인했다.

- `MarketAnalysis`/`MarketIndicator`는 이미 충분히 범용적이라 **모델 변경 없이** v1을 구현할 수 있다.
- Market Agent의 입력 contract는 Stock Research Agent의 `stock_code`가 아니라 **`as_of_date`(+ 내부 lookback)** 여야 한다 — 금리/환율/지수는 시점 하나만으로는 fact가 빈약하고, 구간 대비 변화가 있어야 의미가 생긴다.
- ECOS 실제 API(`StatisticItemList`/`StatisticSearch`, `.env`의 실 키 사용)로 직접 조회해 stat_code/item_code를 **추측 없이 검증**했다:

  | 지표 | STAT_CODE | ITEM_CODE1 |
  | --- | --- | --- |
  | 한국 기준금리 (기존) | `722Y001` | `0101000` |
  | 원/달러 환율 | `731Y001` | `0000001` |
  | KOSPI지수 | `802Y001` | `0001000` |
  | KOSDAQ지수 | `802Y001` | `0089000` |

  부수 발견: `802Y001` 테이블에 외국인 순매수(KOSPI `0030000`, KOSDAQ `0113000`)도 이미 존재한다. 지금은 쓰지 않지만(v2 후보), 향후 수급 데이터를 신규 Kiwoom 엔드포인트 없이 ECOS만으로 확장할 수 있다는 뜻이라 기록해둔다.

- 실제 조회 중 발견한 중요한 비대칭: **기준금리는 주말 포함 매일 값이 채워지고, 환율/지수는 영업일에만 존재한다.** 그래서 "N일 전" 계산 방식을 지표별로 다르게 가져가야 한다는 게 설계 단계에서 확정됐다(13.3 참고).
- 가장 중요한 설계 쟁점은 **regime/risk_level을 누가 결정하는가**였다. Stock Research Agent는 `risk_level`을 Python 상수(MEDIUM)로 고정했지만, Market Agent에서 regime/risk_level은 에이전트의 존재 이유 자체라 상수로 고정할 수 없다. 대안으로 LLM이 `suggested_regime`/`suggested_risk_level`을 제안하되, 어떤 fact에 근거했는지 `regime_fact_ids`/`risk_fact_ids`로 반환하게 하고 Python이 그 fact가 실제로 존재하는지 검증하는 **fact-id grounding**을 제안했다.

### 13.2 Grounding 정책 확정 — 엄격 검증 + 1회 재시도

grounding 실패 시 어떻게 처리할지 두 가지 안을 제시했다:

- 안(A): 유효하지 않은 참조만 조용히 걸러내고 confidence를 LOW로 캡핑
- 안(B): grounding 실패를 근거 없는 결과로 간주해 `ReasoningError`로 처리

**B로 결정했다.** 이유: regime/risk_level은 Market Agent의 핵심 판단이므로, confidence만 낮춰 반환하는 것보다 "근거 없는 결과는 반환하지 않는다"는 프로젝트 원칙을 그대로 지키는 쪽이 더 중요하다는 판단이다. 다만 매번 즉시 실패시키지 않고, JSON 파싱 실패와 동일하게 **1회 재시도 후에도 실패하면 `ReasoningError`**를 raise하는 구조로 만들었다(기존 `DEFAULT_MAX_ATTEMPTS=2`와 동일한 재시도 횟수).

정책은 엄격하게 세 가지를 모두 실패로 처리한다:

- `regime_fact_ids`가 비어 있으면 실패
- `risk_fact_ids`가 비어 있으면 실패
- 존재하지 않는 fact_id가 하나라도 섞여 있으면 실패 (일부 valid id만 남겨 조용히 통과시키지 않음)

# 14. Portfolio Strategy Agent v1 구현 (세션 3)

## 14.1 설계 검토 먼저 진행 (재시작)

세션 도중 한 번 중단되어, 구현 전에 설계 검토를 처음부터 다시 진행했다(코드 수정 없이 README, Market Agent/Stock Research Agent 코드, `PortfolioContext`/`InvestorProfile`/`StrategyResult`/`PositionRecommendation` 모델을 다시 근거로 확인). 핵심 결론:

- **로드맵 순서를 바꿨다.** README는 원래 "Recommendation Engine → Portfolio Strategy Agent" 순서였지만, `app/recommendation/`이 아직 없어 `RecommendationResult`를 줄 수 없다는 사실을 확인했다. Portfolio Strategy Agent v1은 이 입력 없이도 (보유 종목 + 호출자가 명시적으로 분석 요청한 종목만으로) 독립적으로 설계·구현 가능하다고 판단해 먼저 진행했다.
- **모델 변경 없음.** `StrategyResult`/`PositionRecommendation`은 이미 v1에 충분했다(Market Agent 때 `MarketAnalysis`를 그대로 재사용한 것과 동일한 결론). 부족한 것은 모델이 아니라 orchestration 정책이었다.
- **최소 input contract**: `MarketAnalysis + list[StockAnalysis] + PortfolioContext + InvestorProfile`. `stock_analyses`에 없는 보유 종목은 recommendation 대상에서 제외한다(근거 없으면 생성하지 않는다).
- **가장 중요한 설계 문제 — target_weight**: Stock Research Agent의 `target_price`와 동일한 문제로 봤다. 포지션 사이징 근거(리스크 버짓, 밸류에이션 모델 등)가 v1에 전혀 없으므로, `target_weight`는 항상 `None`으로 강제하기로 결정했다. `reasoning.py`의 응답 스키마 자체에 숫자 필드를 아예 넣지 않아 LLM이 값을 만들 통로가 없게 했다.
- **action(BUY/SELL/HOLD 등)은 LLM이 제안**하되(Market Agent의 regime/risk_level과 동일하게 Python 상수로 고정할 근거가 없는 핵심 판단이므로), 보유 여부에 따른 물리적 제약(미보유: BUY/AVOID만, 보유: ADD/HOLD/REDUCE/SELL만)을 Python이 구조적으로 검증하기로 했다.
- **fact-id grounding을 확장**: Market Agent의 `regime_fact_ids`/`risk_fact_ids` 패턴을 재사용하되, "종목 목록 밖의 새 종목을 지어내지 않는가"(symbol grounding)까지 함께 검증하는 **symbol/fact-id/action 3중 grounding**으로 설계했다.
- **섹터 집중도는 v1에서 제외**했다 — Kiwoom(`KiwoomStockInfo`)·OpenDART(`OpenDartCorporation`/`KeyFinancials`) 어디에도 업종/섹터 필드가 없음을 실제 코드로 확인했다.
- **max_confidence는 v1에서 HIGH를 절대 반환하지 않는다.** `stock_analyses`가 하나라도 있으면 MEDIUM, 없으면 LOW — 새 threshold나 점수 모델을 추가하지 않고 기존 두 Agent와 동일한 "핵심 입력 존재 여부" 판정 방식을 그대로 따랐다.

## 14.2 retry boundary 확정

사용자 지시로 다음을 명확히 했다:

- symbol validation, fact-id grounding, allowed-action validation **세 가지 모두 `reasoning.py`의 동일한 재시도 루프 안에서 처리**한다(검증 실패 → 재시도, 최종 실패 → `ReasoningError`).
- `orchestrator.py`는 이 검증을 중복 구현하지 않고 target_weight=None 강제, confidence cap, evidence 조립, 최종 `StrategyResult` 조립 등 orchestration 정책에만 집중한다.

## 14.3 구현

```text
app/agents/portfolio/
├── analysis.py       # deterministic 분석 (portfolio/market/종목 fact, 종목별 allowed_actions)
├── reasoning.py       # LLM reasoning (symbol/fact-id/action 3중 grounding, 재시도 루프)
└── orchestrator.py    # target_weight=None 강제, confidence cap, evidence 조립, StrategyResult 조립
```

- `analysis.py`: 현금 비중, 주식 노출 비중, top1/top3 집중도, 종목별 현재 비중·평가손익률·risk_level·confidence를 모두 평가어 없는 raw fact로 생성한다(fact id 컨벤션은 Market Agent와 동일하게 flat list + 종목 prefix). 보유 여부에 따라 `allowed_actions`(held: ADD/HOLD/REDUCE/SELL, unheld: BUY/AVOID)를 구조적으로 계산한다.
- `reasoning.py`: `_validate_result()`가 symbol grounding(`recommendations[].symbol` ⊆ 판단 대상 종목), action grounding(보유여부에 맞는 action인지), fact-id grounding(recommendation별 + portfolio_risk 각각)을 모두 같은 재시도 루프 안에서 검증한다. 프롬프트에는 "목록에 없는 종목은 절대 언급하지 마라, 포함 시 응답 전체가 무효 처리된다"를 가장 중요한 규칙으로 명시했다(14.4 참고, 실제 E2E에서 필요성이 드러남).
- `orchestrator.py`: `PositionRecommendation` 조립 시 `target_weight=None`을 명시적으로 강제한다(스키마에 필드가 없어 구조적으로도 이미 불가능하지만, 조립 지점에서도 이중으로 보장). `evidence`는 `analysis_result.facts`로만 구성한다(다른 두 Agent와 동일 원칙).

## 14.4 실제 E2E 검증 — 실제 계좌 전체

`scripts/portfolio_strategy_demo.py`(신규)로 실제 Kiwoom 계좌(보유 종목 다수 + ETF 포함) + OpenDART + ECOS + OpenAI를 연결해 여러 차례 실행했다. 이 과정에서 Portfolio Strategy Agent 자체와 무관한 기존 Service 버그 2건, 그리고 grounding 프롬프트 보강이 필요한 문제 1건을 발견했다.

### 문제 1 — Kiwoom 계좌 종목코드에 시장 접두문자가 그대로 남음

계좌평가잔고(`kt00018`) 응답의 `stk_cd`가 실제로는 `"A000660"`처럼 시장 구분 접두문자가 붙어 내려왔다. 이 코드를 그대로 `PortfolioContext.positions[].symbol`에 담아 OpenDART에 넘기면 `"OpenDART corporation not found: A000660"`으로 실패했다. 기존 mock 테스트는 접두문자 없는 값만 가정하고 있어 이 버그를 잡지 못했다(실제 API로만 발견됨).

수정: `KiwoomService._parse_account_positions()`에 `_normalize_stock_code()`를 추가해 7자리(`영문 1자 + 숫자 6자리`) 코드에서 접두문자를 제거한다. `get_stock_info` 등 다른 Kiwoom API는 원래 접두문자 없는 순수 코드를 기대하므로, 다른 것이 아니라 계좌잔고 응답이 예외적으로 접두문자를 붙인다고 판단했다. `tests/test_kiwoom_service.py`에 정규화 테스트 추가.

### 문제 2 — OpenDART 금액 필드의 "-" placeholder 파싱 실패

`OpenDartService._parse_amount()`는 `None`/빈 문자열만 처리했는데, 실제 응답에는 값이 없는 계정 항목이 빈 문자열이 아니라 `"-"` 자체로 내려오는 경우가 있었다(`ValueError: invalid literal for int() with base 10: '-'`). 실제 음수 금액(`"-1,234"`)과 구분해야 하므로, 콤마 제거 후 문자열이 정확히 `"-"`(또는 `"+"`)일 때만 `None`으로 정규화하도록 수정했다. `tests/test_opendart_service.py`에 placeholder 케이스와 실제 음수 케이스를 모두 회귀 테스트로 추가.

### 문제 3 — 계좌에 ETF가 섞여 있을 때

계좌에 ETF(233740 등 4종목)가 포함되어 있었는데, ETF는 기업이 아니라 OpenDART에 재무데이터가 없어 Stock Research Agent가 실패했다. 이건 버그가 아니라 "Stock Research Agent가 애초에 지원하지 않는 자산군"이므로, 데모 스크립트에서 종목별로 실패를 잡아 건너뛰고(`StockAnalysis` 없이) 나머지로 계속 진행하도록 처리했다. 이는 정확히 설계에서 의도한 동작이다 — 핵심 분석 근거가 없는 종목은 recommendation 대상에서 제외되고, portfolio-level fact에는 계속 반영된다.

### 문제 4 — grounding이 실제로 막아낸 진짜 사례

ETF 스킵 이후 남은 종목들로 Portfolio Strategy Agent를 처음 실행했을 때, LLM이 판단 대상 종목 목록에 없는 "에코프로비엠(247540)"을 recommendations에 포함시켰다(실제로는 계좌에 보유 중인 종목이었지만, 그 시점엔 아직 `stock_analyses`에 포함되지 않은 상태였다). Symbol grounding이 이를 정확히 잡아내 검증 실패 → 재시도 → 재시도에서도 동일하게 실패 → `ReasoningError`로 전파했다. **이건 버그가 아니라 grounding이 설계대로 작동한 사례**다 — 근거 없이(주어지지 않은 종목을) 생성하는 것을 구조적으로 막았다.

다만 재시도 2회 안에 복구되지 못했으므로, 프롬프트에서 "목록 밖 종목 언급 금지"를 가장 앞에 오는 최우선 규칙으로 재배치하고 문구를 강화했다("당신이 실제로 알고 있는 유명한 종목이라도 절대 언급하지 마라", "무효 처리되고 재시도된다", "빈 배열을 반환하는 것이 종목을 지어내는 것보다 항상 낫다"). 이후 재실행에서는 동일 문제가 재현되지 않았다(6절 참고). Stock Research Agent의 catalyst 정의를 좁혔던 것과 같은 종류의 "prompt-only" 보강이며, 완전한 기계적 보장은 아니다(symbol/fact-id/action grounding처럼 구조적으로 100% 막을 수 있는 것과는 다르다 — 근본적으로는 grounding이 이미 100% 막고 있고, 이번 보강은 "1~2회 재시도 안에 더 잘 복구되게" 하는 것에 가깝다).

### 문제 5 — LLM 응답 타임아웃

Portfolio Strategy Agent의 프롬프트(전체 fact + 판단 대상 종목 목록)가 Market/Stock Research Agent보다 길어, 기본 30초 timeout 안에 응답이 오지 않는 경우가 실제로 있었다(`httpx.ReadTimeout`). `reasoning.py`의 재시도 루프는 JSON/grounding 검증 실패만 잡고 네트워크 예외는 잡지 않으므로 즉시 예외로 전파됐다 — 이는 Market/Stock Research Agent와 동일한 기존 동작이라 그대로 두고, 데모 스크립트에서만 `LLMService(timeout=90.0)`으로 완화했다.

### 최종 성공

위 5가지를 모두 해결한 뒤, 실제 계좌(보유 종목 24개 중 ETF 4개 제외 20개) 전체로 정상적으로 `StrategyResult`가 생성됐다. 확인된 것:

- `target_weight`는 모든 recommendation에서 예외 없이 `null`이었다.
- 20개 종목 중 6개만 recommendation이 생성되고 나머지는 생략됐다(판단 근거가 부족한 종목을 억지로 채우지 않음, 설계대로).
- action은 ADD/REDUCE/SELL/HOLD만 나왔고(모두 보유 종목이라 물리적으로 맞음), BUY/AVOID 오용 없음.
- `confidence: medium` (HIGH 없음), `portfolio_risk: medium`.
- 각 recommendation의 rationale이 실제로 인용한 fact(비중, 평가손익률 등)와 일치했다.

## 14.7 현재 한계

- v1은 `RecommendationResult`를 입력으로 받지 않는다 — "미보유 종목 추천"은 호출자가 명시적으로 `stock_analyses`에 포함한 종목에 한정되고, 전체 시장을 스캔한 신규 발굴은 Recommendation Engine 완성 후 v2에서 다룬다.
- `target_weight`가 v1에서 항상 `null`이라 "얼마나" 매수/축소할지는 여전히 사용자 판단에 맡긴다 — 포지션 사이징 방법론이 생기기 전까지는 의도된 제약이다.
- 섹터 집중도를 계산할 수 없다(Kiwoom/OpenDART 어디에도 업종 데이터 없음).
- symbol/fact-id/action grounding은 구조적으로 100% 검증되지만, "인용한 fact들이 논리적으로 그 action을 지지하는가"는 검증하지 않는다(Market Agent의 regime/risk_level과 동일한 한계).
- LLM 응답이 길어질수록(판단 대상 종목이 많을수록) 기본 30초 timeout에 걸릴 가능성이 있다 — v1은 이를 재시도 대상으로 다루지 않는다(Market/Stock Research Agent와 동일).
