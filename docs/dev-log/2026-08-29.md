## 1. RE-04 Final Recommendation Architecture — Pipeline

Stock Research Recommendation의 전체 구조를 다음 pipeline으로 확정했다.

```text
User
  → Supervisor / Router
  → Stock Research Agent
  → Data Acquisition
  → Normalized Research Data
  → Deterministic Feature Layer
  → Independent Component Evaluators
  → Core Attractiveness / Market Confirmation
  → Opportunity State
  → Risk + Coverage + Confidence
  → Recommendation Policy
  → Structured StockRecommendation
  → Grounded LLM Explanation / Presentation
```

### Architecture principles

1. Data Acquisition / Feature Calculation / Component Evaluation / Aggregation / Guardrail / Presentation을 분리한다.
2. External Service는 raw/normalized grounded data를 제공한다.
3. 계산 가능한 값은 deterministic하게 계산한다.
4. Component Evaluator가 외부 API를 직접 호출하지 않는다.
5. Risk / Coverage / Confidence는 Attractiveness와 독립적으로 유지한다.
6. LLM은 numeric scoring/calculation engine으로 사용하지 않는다.
7. LLM은 structured evidence/result를 기반으로 explanation/synthesis에 사용한다.
8. `NO DATA != NEUTRAL`.
9. Component failure가 전체 Stock Research failure를 의미하지 않는다.
10. Evidence lineage를 유지한다.

이 원칙들은 이 프로젝트가 RE-01 이전부터 지켜온 "근거 없이 만들지 않는다" / "LLM은 tool-calling·numeric scoring 권한이 없다" / "부분 실패가 전체 실패를 의미하지 않는다"는 기존 원칙(Supervisor/Market Agent/Stock Research Agent v1에서 이미 확립됨)을 Recommendation Engine 레벨로 명시적으로 확장한 것이다.

## 2. Component Architecture — 확정

### Core Attractiveness

중기 투자기회 자체의 핵심 매력도를 의미한다.

- Fundamental Quality
- Valuation Attractiveness
- Forward Opportunity
- Investor Flow

Investor Flow는 기업의 intrinsic value라는 의미가 아니라 **중기 투자기회의 positioning/evidence**라는 의미에서 Core에 포함한다.

### Market Confirmation

- Momentum
- Technical Confirmation

Market Confirmation은 Core Attractiveness score를 직접 수정하지 않는다. 예를 들어:

```text
Core = HIGH
Market = WEAK
```

상태를 그대로 보존하여 아직 가격에 충분히 반영되지 않은 `Early Opportunity` 가능성을 표현할 수 있어야 한다.

### Opportunity State

Core Attractiveness × Market Confirmation으로 생성한다. 개념 예:

- HIGH Core + WEAK Market → `EARLY_OPPORTUNITY`
- HIGH Core + STRONG Market → `CONFIRMED_OPPORTUNITY`
- LOW Core + STRONG Market → `MOMENTUM_DRIVEN`

정확한 score threshold와 enum mapping은 **RE-05**에서 결정한다(이번 세션에서 확정하지 않음).

## 4. Risk — 확정

Risk는 Attractiveness score에서 차감하지 않는다.

v1 기존 Risk:

- Market Risk
- Fundamental Risk

구조:

```text
Base Risk
  +
Cross-Component Risk
  →
RiskResult
```

`RiskResult`는 최소 다음 의미를 지원한다:

```text
RiskResult
├── risk_level
├── risk_dimensions
├── risk_factors[]
├── mitigating_factors[]
├── risk_flags[]
├── coverage
├── confidence
└── evidence[]
```

**High Attractiveness + High Risk도 정상적인 결과다.** Data uncertainty / missing data는 Risk가 아니라 Coverage/Confidence 문제다.

## 5. Coverage / Confidence — 확정

Coverage와 Confidence는 완전히 분리한다.

**Coverage** — 필요한 evidence가 얼마나 존재하는가?

- Required / Supporting / Optional evidence contract를 사용한다.
- Required evidence 부족 시 component eligibility gate가 실패할 수 있다.

**Confidence** — 존재하는 evidence를 얼마나 신뢰할 수 있는가?

주요 요인:

- Data Reliability
- Freshness
- Evidence Agreement
- Sample Sufficiency

Freshness 판단에 필요한 timestamp/status는 **Data Layer가 제공**하고 **Confidence Layer는 이를 평가**한다(책임 분리).

Component-level insufficient evidence와 Recommendation-level `INSUFFICIENT_EVIDENCE`를 구분한다.

## 6. Stock Research vs Portfolio Strategy — 확정

**Stock Research**: "이 종목 자체가 현재 어떤 투자기회인가?"

출력:

- Core Attractiveness
- Market Confirmation
- Opportunity State
- Risk
- Coverage
- Confidence
- Stock Recommendation
- Evidence

**Portfolio Strategy**: "그렇다면 실제 내 포트폴리오에서 무엇을 해야 하는가?"

```text
Stock Research 결과
  +
actual holdings / average price / position weight / cash /
sector concentration / InvestorProfile / portfolio risk
  →
BUY / ADD / HOLD / REDUCE / EXIT / Target Weight
```

**Stock Research에서 개인화된 주문/비중 결정을 생성하지 않는다.** 이 경계는 기존 Portfolio Strategy Agent v1이 이미 지켜온 "종목 자체 분석과 개인화 판단을 분리한다" 원칙(dev-log `2026-08-27.md` 참고)을 Recommendation Engine 도입 이후에도 그대로 유지한다는 뜻이다.

## 7. AS_OF 원칙 — 신규 확정

모든 Stock Research 분석에는 명시적인 분석 기준시점 `as_of` 개념을 두는 방향으로 확정했다.

어떤 evidence도:

```text

```

이면 해당 분석에 사용하면 안 된다.

목적:

- historical recommendation reproduction
- future backtesting
- look-ahead bias 방지
- evidence snapshot traceability

이 원칙은 RE-03.4에서 발견한 "historical valuation 재구성 시 look-ahead bias를 만들지 않는다"는 제약과 직접 연결된다 — `as_of`가 architecture 차원에서 이 문제를 구조적으로 방지하는 장치다.

## 9. Event Source Architecture — 확정

**Official Disclosure**: OpenDART를 v1 primary official source로 사용한다. OpenDART는 두 용도로 분리한다.

```text
기존: OpenDART → Financial Statements → Fundamental
신규: OpenDART → Recent Disclosures → Event Intelligence
```

공시 pipeline은 가능한 경우 다음을 우선한다:

```text
Disclosure Search → Structured Disclosure API → deterministic parsing
```

구조화 API로 충분하지 않은 경우에만:

```text
Original Disclosure Document → document parsing / constrained LLM extraction
```

**News**는 provider abstraction을 둔다. Recommendation Engine이 특정 뉴스 provider에 직접 의존하지 않도록:

```text
EventIntelligenceService → NewsProvider interface/protocol → actual provider
```

구조를 사용한다. **뉴스 provider의 최종 선택은 아직 확정하지 않았다**(§20 참고).

## 10. Event Acquisition / Lifecycle — 확정

v1 initial acquisition 기본안:

- Official Disclosure: 90-day lookback
- News: 30-day lookback

하지만 **`Lookback != Event Validity`**다. Event relevance는 단순 age보다 lifecycle을 우선한다.

Event lifecycle: `NEW` / `ACTIVE` / `RESOLVED` / `SUPERSEDED` / `EXPIRED`

Freshness semantic state: `CURRENT` / `RECENT` / `AGING` / `STALE`

오래된 사건이라도 `ACTIVE`라면 현재 투자판단에 남을 수 있고, 최근 사건이라도 공식 부인/해결됐다면 active catalyst/risk로 남겨서는 안 된다.

향후 Event Store는 incremental update가 가능한 구조를 고려한다(설계만, 구현 아님).

## 11. Event Normalization — 확정

핵심 원칙: **`Event != Article`** — 여러 뉴스/공시가 같은 현실 사건을 다룰 수 있다.

Pipeline:

```text
Source Document
  → Evidence Capture
  → Fact / Claim Extraction
  → EventCandidate
  → Dedup / Matching
  → Verification
  → InvestmentEvent
  → Investment Interpretation
```

- Structured source → deterministic extraction 우선
- Unstructured news/document → schema-constrained LLM 사용 가능
- LLM은 evidence에 없는 사실/숫자를 생성해서는 안 된다.
- 모든 extracted claim은 supporting evidence로 역추적 가능해야 한다.

**Fact와 Interpretation을 분리한다.** 예:

```text
FACT:
  contract_amount = ...
  recent_revenue = ...

DERIVED:
  contract_to_revenue_ratio = deterministic calculation

INTERPRETATION:
  direction / materiality / affected dimension
```

## 15. Deduplication & Cross-Verification — 확정

세 가지를 분리한다:

1. 같은 현실 사건인가? → **Event Matching**
2. 같은 원출처의 복제인가? → **Source Independence**
3. 주장은 얼마나 검증됐는가? → **Cross Verification**

중요 원칙:

- `Document != Evidence != Event`
- 기사 개수 != Event 개수
- 기사 개수 != independent source count
- 여러 기사가 같은 통신사/원문을 재인용하면 독립 Evidence로 보지 않는다.
- multiple sources는 Event magnitude를 증가시키는 것이 아니라 **verification/confidence를 높일 수 있다**.
- majority vote로 사실을 결정하지 않는다.
- correction/supersession과 contradiction을 구분한다.
- AS_OF / temporal precedence를 적용한다.
- deterministic matching first, LLM semantic matching fallback.
- `SAME_EVENT` / `DIFFERENT_EVENT` / `UNCERTAIN`을 허용한다.

## 16. Claim-Level Verification — 확정

Event-level verification만으로는 부족하므로 claim-level verification을 지원한다. 예:

```text
공급계약 존재                    → CONFIRMED
계약금액                        → CONFIRMED
고객사가 NVIDIA라는 뉴스 claim    → UNCONFIRMED 또는 CORROBORATED
```

Event-level verification은 주요 claim 상태를 요약한다.

Verification status: `CONFIRMED` / `CORROBORATED` / `UNCONFIRMED` / `CONTRADICTED` / `UNKNOWN`

`CONFIRMED`는 relevant official primary evidence가 해당 claim을 실제로 확인할 때 사용한다. **공식 문서가 존재한다는 이유만으로 관련 뉴스의 모든 claim을 `CONFIRMED` 처리하지 않는다.**

## 17. Verification != Confidence — 확정

- **Verification**: "사실이 얼마나 확인됐는가?"
- **Confidence**: "이 Event의 투자적 interpretation을 얼마나 신뢰할 수 있는가?"

예: 공급계약 체결 → `CONFIRMED`. 하지만 향후 수익성 영향 → `UNKNOWN`일 수 있다.

Event confidence는 향후 다음 요인을 고려할 수 있다: Evidence Reliability / Verification Strength / Source Independence / Fact Completeness / Interpretation Certainty. **정확한 formula는 아직 정하지 않는다**(§20).

## 23. RE-04 Amendment 1 — Step 6~14 Final Freeze (같은 날짜, 이어지는 세션)

§1~§22는 이 날짜의 첫 세션 기록이며 그대로 보존한다. 이 섹션은 같은 날짜에 이어진 두 번째 세션의 기록이다 — §22가 다음 세션 과제로 남긴 **Amendment Step 6(Materiality & Impact Model)**부터 시작해 **Step 14(Amendment v1 Scope Freeze)**까지 전부 마저 확정했다. 이 세션도 **문서/설계 전용**이다 — production code, test code, model, service, API 구현은 전혀 변경하지 않았고, 임의의 numeric threshold/weight/score/calibration 값도 추가하지 않았다.

### 23.1 Step 6 — Materiality & Impact Model — FROZEN

Materiality semantic:

```text
Materiality
= Event가 기업의 economic state 또는 investment thesis에
  얼마나 중요한 영향을 줄 수 있는가

Materiality != Direction
Materiality != Risk
Materiality != Confidence
Materiality != Verification
Materiality != Priced-In
```

Materiality level: `HIGH` / `MEDIUM` / `LOW` / `UNKNOWN`.

```text
Missing != LOW
Invalid != LOW
Estimated != Actual
UNKNOWN != NEUTRAL
```

Quantitative architecture — 책임을 3단으로 분리한다:

```text
Facts
  ↓
EventMaterialityEvaluator   (계산 가능한 사실/metric/formula)
  ↓
Metrics
  ↓
MaterialityPolicy + PolicyConfig
  (Policy = 계산 결과가 어떤 semantic level을 의미하는가)
  (PolicyConfig = threshold / dimension role / calibration configuration)
  ↓
MaterialityAssessment
```

**Numeric threshold는 여기서 정하지 않는다 — RE-05로 DEFERRED.** §20에서 검토 예시로 들었던 `contract_amount/recent_revenue`, `issuance_amount/market_cap` 같은 formula 후보와 HIGH/MEDIUM/LOW 경계값도 이번에 확정하지 않았다 — Evaluator가 만드는 것은 semantic calculation이고, 그 값을 어느 level로 분류할지는 PolicyConfig(RE-05)의 몫이라는 경계만 이번에 고정했다.

Contextual Materiality:

```text
Context Factors
- TARGET_SCOPE
- COMPANY_RELEVANCE
- IMPACT_DIRECTNESS
- PERSISTENCE

Magnitude
- ECONOMIC_EXPOSURE
- STRUCTURAL_SIGNIFICANCE
```

`ImpactPath`는 Event Interpretation 전반(§23.3의 Investment Interpretation 포함)에서 공유하는 공통 primitive다:

```text
ImpactPath
source_entity
target_entity
steps[]
directness
```

각 causal step은 evidence-supported이거나 inference로 명시되어야 한다 — 근거 없이 causal step을 생성하지 않는다.

**Direction / Realization / Temporal Relevance** (Step 6 semantic의 연장):

```text
Direction
= Event가 특정 economic dimension(FUNDAMENTAL/VALUATION/FORWARD/FLOW/MARKET/RISK)에 미치는 방향

direction: POSITIVE / NEGATIVE / MIXED / NEUTRAL / UNKNOWN / NOT_APPLICABLE
```

```text
Event Type != Direction
Materiality != Direction
Realization != Direction
Expected Impact != Observed Impact
UNKNOWN != NEUTRAL
```

`Realization`은 Materiality와 별도 axis다(예: `RUMORED → PROPOSED → ANNOUNCED → ADOPTED → IMPLEMENTING → EFFECTIVE → COMPLETED → WITHDRAWN → UNKNOWN`) — 구체 enum naming은 implementation detail이며 기존 §12(InvestmentEvent contract)의 `lifecycle`/`verification_status`와 충돌하지 않도록 semantic만 이번에 고정했다.

```text
Freshness != Temporal Relevance
Freshness != Priced-In
Lifecycle != Realization
Elapsed Time != Economic Relevance
```

**Materiality는 단순 시간 경과로 decay시키지 않는다** — universal exponential decay나 `Materiality × time-decay` 같은 구조를 architecture 레벨에서 만들지 않는다(§10의 lifecycle/freshness가 별개 개념이라는 원칙과 일관).

### 23.2 Step 7 — Verification / Confidence Policy — FROZEN

Verification canonical unit은 Event가 아니라 **Claim**이다:

```text
Evidence
  ↓
Canonical Claim
  ↓
ClaimVerification
  ↓
EventVerificationSummary
```

Claim verification status: `CONFIRMED` / `PARTIALLY_CONFIRMED` / `UNVERIFIED` / `CONTRADICTED` / `UNKNOWN`.

```text
UNVERIFIED != FALSE
Source Reliability != Claim Verification
Article Count != Independent Evidence Count
```

가능하면 compound claim은 atomic claim으로 분해한다.

Confidence canonical unit은 **Interpretation**이다(`InterpretationConfidence`, level: `HIGH`/`MEDIUM`/`LOW`/`UNKNOWN`). Confidence factors: `VERIFICATION_STRENGTH` / `FACT_COMPLETENESS` / `INFERENCE_SUPPORT` / `SOURCE_INDEPENDENCE` / `COUNTER_EVIDENCE`.

```text
Verification != Confidence
Coverage != Confidence
Materiality != Confidence
Direction != Confidence
LOW != UNKNOWN
```

Unsupported critical assumption이 있으면 HIGH Confidence를 허용하지 않는다. **정확한 confidence threshold/gating은 RE-05로 DEFERRED.**

### 23.3 Step 8 — Investment Interpretation — FROZEN

`CATALYST` / `HEADWIND` / `RISK` / `CONTEXT`를 하나의 mutually-exclusive Event enum으로 만들지 않는다. **Role은 Event가 아니라 InvestmentInterpretation에 속한다**:

```text
InvestmentEvent
      ↓
ImpactPath[]
      ↓
InvestmentInterpretation[]
      ↓
InterpretationDimensionImpact[]
```

하나의 Event는 여러 `ImpactPath`와 여러 `Interpretation`을 가질 수 있다. 예(Equity Issuance):

```text
Path A: issuance → dilution                          → HEADWIND
Path B: issuance → growth funding → capacity          → CATALYST
Path C: issuance/funding uncertainty                   → RISK
```

```text
Direction != Role
Positive != Catalyst
Negative != Headwind
Uncertainty != Risk
Context != Irrelevant
Context != Low Materiality
```

Interpretation lifecycle은 Event lifecycle과 별도로 유지한다: `ACTIVE` / `RESOLVED` / `SUPERSEDED` / `EXPIRED`. Role과 Status는 독립이다. Historical Interpretation은 overwrite하지 않고 §7(AS_OF 원칙)과 일관되게 AS_OF-safe lineage를 유지한다.

### 23.4 Step 9 — Existing Component Relationship Audit — FROZEN

기존 Recommendation component(§1~§2의 Core Attractiveness/Market Confirmation)와 Event Intelligence의 관계를 다음과 같이 최종 확정한다.

**Event Intelligence는 기존 Component score를 대체하거나 직접 수정하지 않는다** — Event Overlay는 병렬 Recommendation input이다:

```text
Fundamental ────────┐
Valuation ──────────┤
Forward ────────────┤
Flow ───────────────┤
                    ├→ Recommendation Policy
Market Confirmation ┤
Event Overlay ──────┤
Risk/Coverage/Conf ─┘
```

Semantic boundary(용어 혼동 금지):

```text
Fundamental = current / observed economic state
Forward     = future economic outcome
Catalyst    = identifiable driver of change
Valuation   = current price attractiveness
Priced-In   = interpretation-specific market incorporation
Investor Flow        = observed investor capital behavior
Market Confirmation  = current price/trend confirmation
```

```text
Forward != Catalyst
Valuation != Priced-In
Priced-In != Market Confirmation
Flow != Market Confirmation
Catalyst != Market Confirmation
Catalyst != Flow confirmation
```

**Market Confirmation은 economic truth judge가 아니다** — Market Confirmation 부재가 economic opportunity 부재를 의미하지 않는다(§2의 `HIGH Core + WEAK Market → EARLY_OPPORTUNITY` 원칙과 일관).

**Priced-In Assessment** — canonical unit은 Event가 아니라 `InvestmentInterpretation`이다:

```text
PricedInAssessment
interpretation_id
level            # LOW / PARTIAL / HIGH / UNKNOWN
factor_assessments[]
```

v1 factors: `PRIOR_EXPECTATION` / `EVENT_SURPRISE` / `PRICE_REACTION` / `POST_EVENT_INCORPORATION`.

```text
Priced-In != Price Reaction
Priced-In != Valuation
Priced-In != Market Confirmation

No price move != LOW Priced-In
Large price move != HIGH Priced-In
No evidence of pricing-in != evidence of not priced-in
```

**Priced-In 자체는 directional positive signal이 아니다.** `Positive Catalyst + LOW Priced-In → possible remaining upside`, `Negative Headwind + LOW Priced-In → possible remaining downside`. 따라서 **`Priced-In LOW != BUY`**다 — Priced-In level만으로 방향성 판단을 내리지 않는다.

**Correlation / Double Counting / Conflict** — semantic independence와 causal independence를 구분한다. 예:

```text
Supply Contract → Catalyst → EPS Revision → Forward Positive
  → Forward PER → Valuation → Price Reaction → Momentum
```

이들은 서로 다른 semantic question에 답하지만 동일 causal origin을 공유할 수 있다 — 따라서 Recommendation Policy까지 provenance(shared evidence / shared Event / shared ImpactPath / derived-data dependency / explicit causal attribution / temporal relationship)를 유지해야 한다.

Correlation semantic: `SAME_CAUSAL_ORIGIN` / `PARTIALLY_OVERLAPPING` / `INDEPENDENT` / `UNKNOWN`. **정확한 numeric discount는 RE-05로 DEFERRED**(§19의 Double Counting Guardrail 원칙을 그대로 계승, 이번에 숫자를 정하지 않음).

```text
Correlation != Signal Conflict
```

Conflict는 signal들이 서로 다른 investment implication을 보이는 상태다(예: economic thesis positive BUT flow/market confirmation negative). **Conflict는 final output에 보존한다 — Signal Conflict != automatic downgrade.**

### 23.5 Step 10 — Recommendation Policy Integration — FROZEN

**Stock Research와 Portfolio Strategy의 행동 책임 경계를 다음과 같이 명확히 한다** — §6에서 이미 확정한 "Stock Research에서 개인화된 주문/비중 결정을 생성하지 않는다" 원칙의 구체 contract화다:

```text
Stock Research Agent
        ↓
StockOpportunityAssessment
        ↓
Portfolio Strategy Agent
        +
PortfolioContext
        +
InvestorProfile
        ↓
PortfolioActionRecommendation
```

Research output:

```text
StockOpportunityAssessment
status
├─ ACTIONABLE
└─ INSUFFICIENT_EVIDENCE

classification
├─ ATTRACTIVE
├─ NEUTRAL
└─ UNATTRACTIVE
```

`INSUFFICIENT_EVIDENCE`는 classification이 아니라 **status**로 취급한다(권장 architecture로 확정).

```text
NEUTRAL != UNKNOWN
NEUTRAL != Missing Data
UNATTRACTIVE != SELL
```

Portfolio Strategy가 실제 action(`BUY`/`ADD`/`HOLD`/`REDUCE`/`EXIT`/`NO_ACTION` 등)을 담당한다 — 구체 action enum은 향후 implementation에서 조정 가능하지만 **`Research != Portfolio Decision != Execution`** 책임 경계는 FROZEN이다. 기존 Portfolio Strategy Agent v1의 `target_weight` 항상 null 강제 정책(README 참고)과 일관된 방향이다.

**Recommendation Policy는 staged decision이다 — 단순 weighted sum으로 정의하지 않는다:**

```text
Structured Assessments
        ↓
Decision Eligibility
        ↓
Core Economic Attractiveness
        ↓
Event / Forward Opportunity Context
        ↓
Priced-In / Remaining Impact Context
        ↓
Risk Review
        ↓
Market Confirmation Context
        ↓
Correlation / Conflict Review
        ↓
Coverage / Confidence Guardrail
        ↓
StockOpportunityAssessment
```

이 순서는 numeric scoring order를 의미하지 않는다 — `Fundamental 20% + Forward 20% + Catalyst +10 - Risk 15` 같은 arbitrary weighted architecture를 이번에 만들지 않는다. **Numeric scoring/weight는 RE-05로 DEFERRED.**

Eligibility는 모든 데이터 존재 여부가 아니라 **decision-critical evidence sufficiency**를 기준으로 한다 — missing optional data는 Recommendation을 반드시 막지 않지만, missing critical evidence는 `INSUFFICIENT_EVIDENCE`를 만들 수 있다. Event Overlay는 Core score를 직접 수정하지 않는다(§8/§23.4와 일관). Market Confirmation은 mandatory economic gate가 아니다(§23.4와 일관). Correlation metadata는 final classification strength 판단 전에 고려되어야 한다.

### 23.6 Step 11 — LLM vs Deterministic Logic Boundary — FROZEN

```text
LLM != Calculator
LLM != Threshold Owner
LLM != Scoring Engine
LLM != Recommendation Authority
LLM != Missing-data Imputer
```

책임 분리:

```text
Deterministic : price/financial calculations, ratios, normalization, derived metrics, formula evaluation
Policy        : threshold application, semantic classification, final StockOpportunity classification
```

LLM-assisted 가능 영역(모두 candidate 생성까지만, 최종 결정 권한 아님): claim extraction candidate / atomic claim decomposition candidate / claim-evidence matching candidate / contradiction candidate / contextual relationship reasoning / ImpactPath candidate / missing fact identification / assumption extraction / counter-evidence identification / grounded final explanation.

LLM이 생성한 structured candidate는 반드시 다음을 통과해야 한다: `Schema Validation` → `Evidence Reference Validation` → `Temporal / AS_OF Validation` → `Policy Validation`. **LLM fallback은 missing-data imputation이 아니다 — 근거가 없으면 UNKNOWN을 반환한다.** 최종 explanation LLM은 structured decision에 없는 새로운 Catalyst/Risk/probability/target price를 만들어서는 안 된다. 이 원칙은 기존 Stock Research Agent v1/Market Agent v1/Portfolio Strategy Agent v1이 이미 지켜온 "LLM은 tool-calling·numeric scoring 권한이 없다" 원칙(README §1)을 Event Intelligence/Recommendation Policy 레벨로 확장한 것이다.

### 23.7 Step 12 — Failure / Missing News / Missing Disclosure — FROZEN

```text
Missing != Neutral
Empty Result != No Event
Failure != Empty Result
Stale != Current
Partial != Complete
Unknown != False
```

`News query success + []`와 `News API timeout`은 다르다. Empty search result도 real-world Event 부재를 증명하지 않는다 — DART도 동일하게 "No matching disclosure found in queried scope"까지만 말할 수 있다. Source failure를 neutral signal로 바꾸지 않는다:

```text
Consensus unavailable != Forward Neutral
Price unavailable      != Market Neutral
News unavailable        != No Catalyst
```

Stale data는 stale로 표시하고, partial pagination/retrieval은 complete result로 취급하지 않는다. Conflicting source는 supporting/contradicting evidence를 모두 보존한다. Alternate source가 semantic requirement를 충족한다면 특정 provider failure가 전체 분석 실패를 의미하지 않고, LLM failure도 deterministic analysis 전체를 실패시키지 않는다 — 이 원칙은 기존 Supervisor v1의 위치별 부분 실패 정책(README §1, root/fan-out/sink)과 일관된 확장이다. AS_OF 이후 evidence는 해당 analysis decision path에서 reject한다(§7과 일관).

Failure propagation:

```text
Source Failure
      ↓
Fact / Metric Availability
      ↓
Affected Assessment
      ↓
Coverage / Confidence
      ↓
Eligibility / Warning
```

### 23.8 Step 13 — Evidence Lineage Final Audit — FROZEN

모든 material recommendation claim은 structured assessment와 grounded evidence까지 추적 가능해야 한다.

일반 lineage: `StockOpportunityAssessment → Decision Reason → Decision Input/Assessment → Metric/Interpretation → Fact/Claim → Evidence → Original Source`

Event path(§18의 기존 lineage를 그대로 계승): `Recommendation → Decision Reason → Catalyst/Headwind/Event Risk → InvestmentInterpretation → ImpactPath → InvestmentEvent → Canonical Claim → Evidence → Original DART/News/IR Source`

Derived metric도 lineage를 가져야 한다(`Input Facts → formula_id/formula_version → Derived Metric`). Policy lineage(`policy_version` / `policy_config_version`)도 추적 가능해야 한다. Temporal provenance는 가능한 경우 `effective_at` / `published_at` / `retrieved_at` / `assessment_as_of`를 구분한다. Supporting evidence뿐 아니라 counter-evidence도 보존하고, Correlation provenance도 Recommendation까지 살아 있어야 하며, Historical Event/Interpretation supersession lineage도 보존한다.

LLM 내부 chain-of-thought 저장은 요구하지 않는다 — 필요한 것은 `input evidence references` / `structured output` / `model·schema·prompt version metadata` / `resolution_method`다.
