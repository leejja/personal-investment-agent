## 1. README Architecture 개선

README의 Overall Architecture를 실제 구현 구조와 일치하도록 수정했다.

전체 데이터 접근 구조는 다음과 같다.

```text
Agent
  │
  │ MCP Client
  ▼
MCP Server
  │
  │ MCP Tool
  ▼
Domain Tool
  │
  ▼
Service
  │
  ▼
External API
```

각 Layer의 책임은 다음과 같이 구분한다.

```text
Agent
→ reasoning / investment decision

MCP Client
→ MCP Tool discovery / invocation

MCP Server
→ Tool exposure / protocol boundary

Domain Tool
→ semantic domain operation

Service
→ external API access / parsing / normalization

External API
→ raw data provider

Model
→ cross-cutting data contract
```

Model Layer는 실행 흐름의 한 단계가 아니라
Service, Tool, Agent, Supervisor 등이 공통으로 사용하는
**Data Contract Layer**라는 점도 README에 명시했다.

현재 실제 Agent는 아직 구현되지 않았으므로 MCP Client 역할은

```text
tests/test_mcp_server.py
```

가 대신 수행한다.

향후에는 Market Agent / Stock Research Agent 등의 Agent Runtime이
실제 MCP Client 역할을 수행한다.

## 2. Recommendation Engine 공식 추가

프로젝트 최종 범위에 **신규 종목 추천 기능**을 추가하기로 결정했다.

Recommendation Engine은 단순 종목 랭킹이 아니라 다음 정보를 함께 고려한다.

```text
MarketAnalysis
StockAnalysis[]
PortfolioContext
InvestorProfile
        │
        ▼
Recommendation Engine
        │
        ▼
RecommendationResult
```

초기 평가 요소는 다음과 같다.

- Fundamental
- Earnings Momentum
- Valuation
- Price Momentum
- Foreign / Institution Flow
- Catalyst
- Risk
- Portfolio Fit
- Market Regime
- Investor Risk Tolerance

추천 구조는 단계적으로 개발한다.

```text
Phase 1
Rule-based / Quantitative Scoring

        ↓

Phase 2
Agent-based Qualitative Evaluation

        ↓

Phase 3
Hybrid Recommendation

Quantitative Score
        +
Agent Reasoning
        +
Portfolio Constraints
```

향후 모델의 예시는 다음과 같다.

```text
RecommendedStock
├── symbol
├── name
├── score
├── recommendation_reason
├── fundamental_score
├── earnings_score
├── valuation_score
├── momentum_score
├── flow_score
├── catalyst_score
├── risk_score
└── portfolio_fit_score
```

```text
RecommendationResult
├── market_context
├── recommended_stocks[]
├── excluded_stocks[]
├── confidence
└── evidence[]
```

특히 추천된 종목의 이유뿐만 아니라

- Risk
- Portfolio Concentration
- Investor Constraint
- Market Condition

등으로 인해 **추천에서 제외된 이유까지 추적 가능**하도록 설계한다.

현재 Recommendation Engine은 Architecture와 개발 계획에 포함되었으며
아직 실제 구현 단계에는 들어가지 않았다.

## 7. 최신 날짜 자동 조회

초기 테스트에서는 다음과 같이 조회 기간이 고정되어 있었다.

```text
start_date = 20260818
end_date   = 20260821
```

이를 개선하여 `end_date`가 테스트 실행 시점의
한국 날짜를 자동으로 사용하도록 변경했다.

```python
from datetime import datetime
from zoneinfo import ZoneInfo

end_date = datetime.now(ZoneInfo("Asia/Seoul")).strftime("%Y%m%d")
```

따라서 향후 테스트 실행 날짜가 변경되어도 자동으로

```text
start_date = 20260818
end_date   = 현재 한국 날짜
```

범위를 조회한다.

예:

```text
2026-08-22 실행

20260818 ~ 20260822
```

```text
2026-08-24 실행

20260818 ~ 20260824
```

## 8. Latest Available Observation 처리 원칙

조회 종료일과 ECOS가 실제 제공하는 최신 관측일이
다를 수 있다는 점을 확인했다.

예를 들어 2026-08-22는 토요일이므로

```text
조회 요청 종료일
20260822
```

까지 요청하더라도 ECOS가 실제 반환한 최신 데이터는

```text
20260821
```

이었다.

따라서 다음 두 개념을 명확하게 구분하기로 했다.

```text
Requested End Date
        │
        │ ECOS query
        ▼
Latest Available Observation
```

중요한 원칙:

**ECOS에 존재하지 않는 날짜의 데이터를 Service Layer에서 임의 생성하지 않는다.**

예를 들어 다음과 같이 처리하지 않는다.

```text
20260821 → 2.75
20260822 → 2.75   ← 임의 생성 금지
```

대신 실제 시스템에서는 다음과 같이 해석한다.

```text
Current Date
2026-08-22
      │
      ▼
Latest ECOS Observation
2026-08-21
      │
      ▼
Base Rate
2.75%
```

향후 Market Agent에서도 동일한 원칙을 적용한다.

예:

```text
현재 확인 가능한 최신 한국은행 기준금리는
2026-08-21 기준 2.75%
```

## 9. Timezone 처리

초기에는 다음 코드를 사용했다.

```python
datetime.now()
```

그러나 Ruff에서 다음 오류가 발생했다.

```text
DTZ005 `datetime.datetime.now()` called without a `tz` argument
```

한국 시장 데이터를 다루는 프로젝트 특성을 고려하여
명시적으로 KST를 사용하도록 수정했다.

```python
from datetime import datetime
from zoneinfo import ZoneInfo

datetime.now(ZoneInfo("Asia/Seoul"))
```

이를 통해 향후 다음 영역에서도 동일한 timezone 기준을 사용할 수 있다.

- 한국 주식 거래일
- 장 시작/종료 시간
- 일봉 기준일
- 공시 시각
- ECOS observation date
- 투자 리포트 생성 시각

수정 후 Ruff 검사를 통과했다.
