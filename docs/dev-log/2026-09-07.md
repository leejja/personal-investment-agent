## J. Step H — Top-level Coverage Aggregation Contract

`RecommendationEvaluationState.coverage`(항상 `None`이던 필드)의
정확한 semantics를 FROZEN했다.

**State Coverage != Core Coverage**: `RecommendationEvaluationState
.coverage`(5개 component 전부, Decision Eligibility evidence
summary)와 `CoreAttractivenessAssessment.coverage`(Core 4-component만,
아직 미구현인 Core Attractiveness producer 소관)를 명확히 구분했다 —
같은 `CoverageAssessment` 타입을 재사용하되 scope가 다른 별개
인스턴스여야 한다. 이번 Step H/I는 State Coverage만 다룬다.

**초기 설계의 오류와 독립 검토를 통한 발견/수정**: 최초 설계안은
`FutureOpportunityEvidence.requirement_satisfied == UNKNOWN`을
top-level `critical_path_satisfied=True`로 취급했다("Forward가 없어도
v1이 진행 가능해야 한다"는 §27.3 FROZEN 원칙을 근거로 들었으나).
독립 검토에서 이것이 `UNKNOWN != FALSE`(FROZEN 원칙)와
`UNKNOWN == PASS`(FROZEN된 적 없는 별개 명제)를 혼동한 것임을
지적받았다 — "아직 판단 못 내림"과 "판단해서 통과시킴"은 다르다.

재검토 결과: `RecommendationEvaluationState`가 "progressively populated
**intermediate** state container"(모델 자체 docstring)라는 사실과,
`RequirementSatisfaction`(tri-state)이 이미 `state.future_
opportunity_evidence`라는 **별도의 손실 없는 필드**로 보존된다는
사실을 근거로, **Forward를 top-level critical bool에서 완전히
제외**하는 것으로 최종 확정했다:

```python
# 폐기된 초기안
forward_gate_satisfied = FOE.requirement_satisfied != NOT_SATISFIED
critical_path_satisfied = Fund AND Val AND forward_gate_satisfied

# FROZEN 최종안
critical_path_satisfied = Fund.critical_path_satisfied AND Val.critical_path_satisfied
# Forward/FutureOpportunityEvidence는 이 bool에 전혀 참여하지 않는다.
```

Forward는 axis별로 역할이 다르다: `critical_path_satisfied`(bool)
축에서는 non-gating, `coverage_status`(4-value enum, "모른다"를
정직하게 표현 가능)축에서는 여전히 자기 자신의 실제 상태를 그대로
반영한다(tier 계산 = Fundamental/Valuation/Forward 3개 status만
사용, Flow/Market 제외). FutureOpportunityEvidence의 tri-state
판정(실제 Decision Eligibility)은 미구현 Recommendation Policy
Step 1의 몫으로 명시적으로 위임했다.
